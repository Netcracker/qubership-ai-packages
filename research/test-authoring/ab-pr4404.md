# A/B trial: implementing a fix with its tests, one-shot against plan-then-write

Run on 2026-09-06 against pgjdbc at the base commit of
[PR #4404](https://github.com/pgjdbc/pgjdbc/pull/4404), with no part of that pull request applied. The pull request
fixes `PGbytea.toPGLiteral`, which wrote every `bytea` parameter as `'\xcafebabe'::bytea` and ignored the
`standard_conforming_strings` flag its context carries, so a server with the setting off, under
`preferQueryMode=simple`, either refused the statement or stored a value the driver never sent. Unlike the
[PR #4405 trial](ab-pr4405.md), the sessions here had to write the fix as well as the tests, from the problem
statement alone; the statement was the pull request's "Why" section with the fix and the tests left out.

The pull request as the maintainer wrote it, before this skill existed, carried the fix through a shared helper, five
unit cases in `PGbyteaTest` (one per input type plus the empty value, all with the setting off), and a parameterized
integration class over four input types, `SIMPLE` and `EXTENDED`, and the setting on and off, with one eight-byte value.
The reviewer's LLM pass found the code correct and raised, on the tests: `assertTrue(a == b)` collapses the failure to
"expected true, was false"; nothing asserts that no warning is drawn, so the stated reason for choosing `E'…'` over a
doubled backslash is untested; "shape" is doing the work of "input type"; the comment on the test data merges two
different UTF-8 cases. On the code: the summary line of `toPGLiteral` still promises the plain form unconditionally,
the input list omits the `String` hex form, the helper is not a "prefix", and the deprecated one-argument overload
still corrupts and says nothing about it.

## Setup

As in the first trial: four headless sessions in detached worktrees at the same commit with `test-authoring`, the
trimmed `javadoc-authoring`, and `english-developer-style` installed with their trigger rules. Arm A: "fix the
problem and write the tests the fix needs, commit". Arm B: "say what fix you will make, then read `test-authoring`
and say which tests it needs; write nothing yet", then "now implement the fix and the tests by that plan". Opus and
Sonnet, one run per cell. The same confound as before: the maintainer's project memory index was in every session's
context, and it holds a note about this very fix, so "the model chose `E'…'`" is not evidence of discovery; the
comparison between arms stands.

Every cell produced the same fix the pull request has, through a helper with a different name each time; every cell
compiled, passed with the fix, went red without it, and passed checkstyle and autostyle. Every cell reported its own
red run, and the two Opus cells named the base-code symptoms per case (`invalid byte sequence`, `invalid input syntax
for type bytea`, `array lengths differ, expected: <4> but was: <7>`). B, Opus also ran the rival fix, a doubled
backslash in a plain literal, and reported that exactly one test told the two apart: the warning assertion. That is
§1 of the skill ("name the production change that would make this test fail") producing the test the reviewer asked
the original pull request for.

Arm B cost about a third more with Opus and 40 percent more with Sonnet. With Opus the plan step again bought input
selection: the two-axis unit table (four input types times the setting), the stream-backed `StreamWrapper` case the
original did not have, the hex `PGobject` bind that A, Opus tried and wrongly concluded was unreachable, and the
side-by-side run of the rival fix. It also produced one wrong claim in the plan (that `PreparedStatement.toString()`
follows the connection's setting and three existing tests would need changing), which the model caught and reverted
in step 2. With Sonnet the plan step bought unit coverage (six branch cases against two) and lost the integration
test: one method, one value, no warning assertion, no version guard.

Three answers, as for the first trial.

**What the new skill settles.** The one test-coverage finding the reviewer raised, the missing warning assertion, is
present in three of four cells, and in one of them with the evidence the reviewer wanted: the rival fix run against
the suite. No cell wrote `assertTrue` around a comparison. Every cell set the server setting inside the test rather
than relying on the CI matrix, which the original also did. The unit coverage per branch is at least the original's in
three cells and beyond it in B, Opus.

**What the review found that the skill does not address.** The code-side findings: the deprecated overload's silent
Javadoc, the unconditional summary line, the incomplete input list, and the helper's name. All four cells left the
deprecated overload alone and three left the summary line as it was, which is `javadoc-authoring` territory (§3 and
§4 there), and that skill was loaded by three cells. The prose findings, "shape" and the data comment, did not recur,
but that is one run each and the cells chose different data layouts rather than better wording.

**What got worse.** Compared with the original pull request, no cell kept the on-and-off, `SIMPLE`-and-`EXTENDED`
integration matrix; every cell tested the off-and-`SIMPLE` corner only, so the negative controls that the original's
parameterized class carried (green on base, red if `E'…'` were emitted unconditionally) exist only in the unit tests,
and only in the two Opus cells and B, Sonnet. Two cells (both Sonnet) have no PostgreSQL 19 guard at all, so their
integration test errors rather than skips on a server that rejects the setting; the original had a per-case
`assumeTrue`. A, Opus dropped the hex `PGobject` bind from the integration test after a wrong conclusion about its
reachability, so that branch is unit-tested only. And the cheapest cell, A, Sonnet, unit-tests two of the four
branches where the original tested all four. None of these is a rule the skill states and the model broke; the
matrix and the guard are things the original author knew about this repository, and the skill has no rule that says
"keep the negative axis in the integration test", which is worth adding to §4 as a decision-table row: the setting
that triggers the bug is one axis, and the value it takes when the bug does not trigger is the control column.
