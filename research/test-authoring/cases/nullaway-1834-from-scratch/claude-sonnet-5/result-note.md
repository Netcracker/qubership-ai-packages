I added five tests to cover the fix in `614efcf`, which had shipped with none. All are red on the pre-fix commit (`09fdea5`) and green on the current one — verified with a scratch worktree, not just claimed.

**In `WildcardTests.java`** (the file already covering `extendsBoundContains`/wildcard containment):
- `typeVariableActualJudgedByDeclaredUpperBound` — the core bug: a bare, unannotated type-variable actual (`Foo<V>` with `V extends @Nullable Object`) passed where `Foo<? extends Object>` is required is now rejected; the control shows a non-null-bound `V` still passes.
- `annotatedTypeVariableActualComparedAsWritten` — the boundary next to that fix: when the actual carries its own `@NonNull`/`@Nullable` annotation, that annotation wins over the declared bound in either direction. This one doesn't fail on the base commit (that half of the logic was already correct), so I verified it a different way: mutating the new `hasNullnessAnnotation` gate to always report "no annotation" makes it fail, confirming it actually exercises that gate rather than passing vacuously.
- `actualBoundCheckedAgainstParametricRequirement` and `annotatedParametricRequirementRejectsNullableBoundActual` — the other branch of the fix, where the *requirement* itself names a type variable (`? extends T`) instead of a concrete type: a nullable-bounded actual is now rejected unless `T` itself admits null, and is rejected too when the requirement is explicitly `? extends @NonNull T`.

**In `GenericInheritanceTests.java`**: `overrideReturnTypeJudgedByDeclaredUpperBoundInExtendsWildcard` — the CHANGELOG calls out that this reaches override checking (`List<V>` overriding `List<? extends @NonNull V>`), which goes through `subtypeParameterNullability`/`CheckIdenticalNullabilityVisitor` via a different caller than direct assignment, so it's worth its own small test rather than assuming the wiring carries over.
