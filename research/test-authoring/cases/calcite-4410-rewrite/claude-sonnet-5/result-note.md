## Message for the PR author

I rewrote the two test methods this commit added (`testSelectJoinUsingCommonColumnCaseSensitive`, `testNaturalJoinCommonColumn`) into four smaller, independently-named tests: `testJoinUsingCommonColumnMatchesCaseInsensitively`, `testJoinUsingCommonColumnAliasKeepsSelectItemCasing`, `testNaturalJoinCommonColumnIsNotAmbiguous`, `testNaturalJoinCommonColumnMatchesCaseInsensitively`.

**Why**: every original case called `.ok()`, which only asserts that validation doesn't throw — it says nothing about *what* got matched or how it was expanded. That's the "passes only because nothing threw" shape: it would stay green even if the fix had matched the wrong column, built an un-coalesced reference, or (as this diff also changes) picked the wrong case for the result alias. I switched to `.rewritesTo(...)`, which checks the validator's actual rewritten SQL — the COALESCE call and the alias it picks — so the test fails if the expansion itself is wrong, not just if it throws.

I confirmed each new test is a genuine regression test by temporarily swapping in the pre-fix `SqlValidatorImpl.java` (from the parent commit) and re-running: all four fail with `Column 'DEPTNO'/'deptno' is ambiguous`, exactly the bug's symptom, then pass again with the fix restored. I did not touch or commit any production code.

I also cut what looked like redundant cases: of the four USING sub-cases, two (`DEPTNO`/`DEPTNO` and `deptno`/`deptno`) exercise the exact same code path as each other and add nothing beyond what `testJoinUsing` already covers — both strings normalize the same way once validated, so I kept one case per mismatched direction instead (`DEPTNO` select vs `deptno` USING, and the mirror). Along the way I learned something worth flagging: the COALESCE operands always print with the *catalog's* canonical column casing (`DEPTNO`), regardless of which case appeared in the USING clause — only the final result alias keeps the literal case the user wrote in the SELECT list. Testing both directions is what actually pins that down; a single direction wouldn't catch an implementation that picked the alias case by some other rule. Similarly for `testNaturalJoinCommonColumn`, the first two sub-cases (`DEPTNO`/`deptno` under `withCaseSensitive(true)`, no casing override) parse to the identical uppercase identifier under this fixture's default unquoted-casing rule, so they're the same case twice; I kept one (`testNaturalJoinCommonColumnIsNotAmbiguous`), which is really testing something broader than the JIRA title suggests: before this fix, NATURAL JOIN never ran the common-column-coalescing logic at all (the old code's early-return only checked `JoinConditionType.USING`), so a bare common-column select from a NATURAL JOIN was always rejected as ambiguous — even with default, fully case-sensitive matching. That's worth a test of its own, independent of case-insensitivity.
