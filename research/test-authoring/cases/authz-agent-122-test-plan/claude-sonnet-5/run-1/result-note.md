## Test plan for 2b4b8ac (kind harnesses → `authz-test-stand` chart)

The commit replaces loose, `kubectl apply`-ed manifests with a parameterized Helm chart and a new Makefile mechanism to drive it, but ships no test of its own for either. The pip-stub default-route change already carries unit tests (`main_test.go`) — this plan is only about the move itself. Two buckets: tests you can add now (no cluster needed), and runs that need `kind`/Docker, which I could not perform here and am only specifying.

### A. Small, no cluster or Docker — chart-render assertions

`test/scripts/test-chart-render.sh` says in its own header it is scoped to "the trusted-provider constructor," so these don't belong there (§9: a test goes beside the unit it exercises). Add a sibling script, `test/scripts/test-stand-chart-render.sh`, in the same idiom (`helm template --show-only`, `pass`/`fail`, `object_count`/`kinds_of`), wired into the `chart` job of `.github/workflows/integration-tests.yaml` right after the existing `Render assertions` step (which already runs after `make test-stand-files`, so `files/` exists).

1. **Each part toggles.** State: default `values.yaml` (everything `enabled: false`/empty). Input: no `-f`. Shows: `helm template` with no overrides renders zero Secret/Deployment/Service for `idp`, `tenantManager`, `clientCredentials`, and zero `pipStub` instances — the "off by default" claim (`values.yaml:1`). Control: the same render with `-f test/k8s/test-stand-values.yaml` produces one of each.
2. **The required-value guards fire with their own message.** State: `test/k8s/test-stand-values.yaml` as base. Inputs/cases, each its own case since the template `fail`s at the first mismatch (one case per guard, not a shared act):
   - `--set TAG=` → `helm template` fails with `TAG is required` (`pip-stub.yaml:40`, `tenant-manager.yaml:34`, `suite.yaml:40`).
   - `--set pipStub.instances.pip-stub.port=` → fails with `pipStub.instances.pip-stub.port is required` (`pip-stub.yaml:2`).
   - `--set clientCredentials.username=` and, separately, `--set clientCredentials.password=` → each fails with its own `required` message (`client-credentials.yaml:11-12`).
   - `--set tenantManager.imageRepository=` → `tenantManager.imageRepository is required` (`tenant-manager.yaml:34`); `--set tenantManager.tenants={}` → `tenantManager.tenants is required` (`tenant-manager.yaml:6-8`).
   - `--set idp.realms=nonexistent` → the chart's own `fail` naming the missing `files/realms/nonexistent/` directory and `make test-stand-files` (`idp.yaml:1-5`).
   Shows: each guard reports the problem it names, not a generic Helm nil-pointer error — the thing a stand operator actually hits when a values file is wrong.
3. **A pip-stub instance with `config` gets a ConfigMap and mount; one without doesn't.** State: `test/k8s/parity/test-stand-values.yaml`, which has exactly this contrast (`pip-mock` has `config: requestargs.responses.yaml`, `entitlements-mock` has none). Shows: `pip-mock-config` ConfigMap and its `volumeMounts`/`volumes` exist only on `pip-mock`'s Deployment, not on `entitlements-mock`'s (`pip-stub.yaml:3-7,45-48,61-72`).
4. **`tenantManager.tenants` joins correctly.** Case: `test/k8s/test-stand-values.yaml`'s single entry renders `TENANT_MANAGER_TENANTS=default=6f1c2a9e-...`. Second case (boundary on the `range`/`append` loop, which no shipped values file exercises): render with `--set tenantManager.tenants.a=1 --set tenantManager.tenants.b=2` and assert the env value is `a=1,b=2` with the comma in the right place (`tenant-manager.yaml:2-5,37-38`).
5. **The realm checksum tracks content, not just presence.** Render `idp.yaml` with `-f test/k8s/test-stand-values.yaml` (realms: e2e) and again with `-f test/k8s/parity/test-stand-values.yaml` (realms: parity) and assert the two `checksum/realms` annotations differ; render the same inputs twice and assert the checksum is stable. Shows the "restarts when a realm file changes" promise (`idp.yaml:34-35`) actually depends on content, and isn't accidentally constant (e.g. from map key order).
6. **Every container the chart can render carries the restricted-PSS context, with Keycloak as the one exception.** Render once with every part turned on (`idp`, two `pipStub` instances — one with `config`, one without —, `tenantManager`, `clientCredentials`, `suite` with `serviceAccount: true`). Enumerate every container block from the output and assert each has `allowPrivilegeEscalation: false` and `capabilities: {drop: [ALL]}`, and `readOnlyRootFilesystem: true` for every container except `keycloak`, which is `false` (`_helpers.tpl:29-40`, used at `idp.yaml:79-80`, `pip-stub.yaml:57`, `tenant-manager.yaml:47`, `suite.yaml:56-57`); assert every Pod template's own `securityContext` has `runAsNonRoot: true` and `seccompProfile.type: RuntimeDefault` (`_helpers.tpl:17-27`). This is an open-set test (§4): it reads the set of containers from the render rather than listing them by name, so a template added later with no security context fails it, instead of passing silently.
7. **Labels.** One render with every part on: every object carries `app.kubernetes.io/part-of: authz-test-stand` and a `helm.sh/chart` value, and the selector stays the bare `app: <name>` the docs promise `kubectl -l app=<name>` works with (`_helpers.tpl:1-15`, `test/k8s/README.md`'s rewritten table).
8. **`E2E_HELM_ARGS` now reaches the test stand (§3, "existing setting reaches a new consumer it didn't reach before").** Before this change `E2E_HELM_ARGS` only reached `authz-agent`/`authz-policy-admin` (`helm-templates/authz-agent/templates/deployment.yaml:154`, `helm-templates/authz-policy-admin/templates/deployment.yaml:80`, both via `Makefile:92-93`); the Makefile comment at `Makefile:46-48` now says it reaches "every chart install, the test stand's included" via `Makefile:86,150`. `test-stand-values.yaml` already sets `IMAGE_PULL_POLICY: Never`, so that documented default doesn't exercise the new path. Test: `helm template helm-templates/authz-test-stand -f test/k8s/test-stand-values.yaml --set IMAGE_PULL_POLICY=Always --set TAG=smoke` and assert the `pip-stub`, `tenant-manager`, and `parity-suite`/`runtime-suite` containers get `imagePullPolicy: Always` and image tag `:smoke`, overriding the values file's own `Never`/`ci` — the same key the old consumers already read at a value meant for them, not the chart's own documented example.
9. **The `emptyDir` size falls back correctly when `ephemeral-storage` is absent from the limits** (`suite.yaml:66-68`, a `dig` with a literal default that no shipped values file currently exercises, since both ship an explicit `ephemeral-storage` limit): render with `--set suite.resources.limits=null` (or only `memory` set) and assert `sizeLimit: 256Mi`.

### B. Small, no cluster or Docker — `profile.jq`

`build/authz-agent-transfer/profile.jq` is new, non-trivial logic (segment classification + capitalization) with zero coverage; a wrong regex or an accidental `//=`→`=` would silently mis-tag the claims the parity goldens were recorded against, and nothing today would catch it. Add `test/scripts/test-profile-jq.sh` in the same `jq`/`pass`/`fail` idiom as `test-chart-render.sh`, run via `jq -n -f build/authz-agent-transfer/profile.jq --argjson in '<literal>' 'profile($in)'` (or equivalent), feeding literal user objects:

1. The worked example from the comment: `{"username":"parity-r29-level-m2m"}` → `firstName:"Parity", lastName:"R29LevelM2M", email:"parity-r29-level-m2m@example.test"`.
2. A username with a single ordinary segment: `{"username":"parity-admin"}` → `lastName:"Admin"` (boundary: one-segment split).
3. A username with no `parity-` prefix: `{"username":"guest-reader"}` → `lastName:"GuestReader"` (shows `ltrimstr` no-ops on the whole string rather than erroring, and the rest of the pipeline still runs on it).
4. **Control for `//=`**: a user that already declares `firstName`, `lastName`, and `email` → `profile()` leaves all three untouched. Every realm/user file in the repo today omits all three, so this is the one case that would catch `//=` silently becoming `=`.

### C. Needs Docker (not run here) — the duplicate-username/-id guard

`build/authz-agent-transfer/Dockerfile:43-46` fails the `chart-files` build if two merged user/realm files share a username or an `id`. No test exercises the failing side; today it passes only because no two files happen to collide. If you can run Docker: add a throwaway second file under `test/parity/suite/testdata/realm/` with a username already used by `parity-realm.json`, run `docker build --target chart-files -f build/authz-agent-transfer/Dockerfile .`, and confirm it fails with the `jq -e` exit rather than silently keeping one of the two users.

### D. Needs `kind` (not run here) — the replaced wait/retry mechanism

Per §3's rule for a change that replaces a mechanism that waits or retries: the old `e2e-suite`/`parity-suite` (`kubectl apply` + `kubectl wait --for=condition=Ready pod ... --timeout=3m`, then `logs -f`, then `wait --for=condition=Complete --timeout=1m`) is now the `run-suite` macro (`Makefile:100-107`): `helm test ... --timeout 15m` run concurrently with `kubectl wait --for=create job/<name> --timeout=2m`, then a log-polling loop of up to 90×2s=180s, then `logs -f`, then `wait $helm_pid`. I don't have the old mechanism's actual failure history (no CI log access, and you asked me not to use `gh`), so I can't name the fault it met most often — please supply that, or pull it from CI history yourself. Separately, on kind: deliberately make the suite Job never get created (e.g. an impossible resource request on `suite.resources.requests.cpu`) and confirm `run-suite` reports a named timeout (what it waited for, what it last saw — §7) within a bounded time, rather than hanging past `helm test`'s 15 m; compare that duration and message against what the old `kubectl wait --for=condition=Ready pod --timeout=3m` used to report on the same fault, and note both in the PR per §3.
