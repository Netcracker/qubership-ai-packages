# A/B trial: the skill on a real fix, one-shot against plan-then-write

Run on 2026-09-06 against pgjdbc at the base commit of
[PR #4405](https://github.com/pgjdbc/pgjdbc/pull/4405) with that PR's one-file fix applied and its test left out. The
fix prefixes a parameter literal with `E` when `standard_conforming_strings` is off, so a server with
`escape_string_warning` on stops sending `nonstandard use of \\ in a string literal` as an `SQLWarning` per bound
parameter under `preferQueryMode=simple`. The pull request as the maintainer wrote it, with an Opus model and without
this skill, carried one integration test class and no unit test, although `V3ParameterListTests` already exercises
`SimpleParameterList.toString` in the same package.

Two questions:

1. Given the problem, the fix, and the trigger rules installed in `.claude/rules/`, does the model load
   `test-authoring` on its own and write the unit test the pull request lacked?
2. Does planning the tests first ("read the skill and say which tests the change needs"), then writing them by the
   plan, produce better tests than writing them in one step, and at what cost?

## Setup

Four headless `claude -p` sessions, one per cell, in separate detached worktrees at the same commit, each with
`test-authoring`, the trimmed `javadoc-authoring`, and `english-developer-style` in `.claude/skills/` and their trigger
paragraphs in `.claude/rules/`. Arm A got one prompt: the problem, the diff, "write the tests this change needs, and
commit". The prompt named no skill and no test class, and said only that a PostgreSQL 16 was on a local port. Arm B got
the same problem and diff with "read the project skill `test-authoring` and say which tests this change needs; write
nothing yet", then, in the same session, "now write the tests by that plan, and commit". Models `opus` and `sonnet`
as the CLI resolved them on the day (Claude Opus 5, Claude Sonnet 5). One run per cell; the numbers below have no
variance estimate.

One confound: the sessions ran in the maintainer's user profile, so the pgjdbc project memory index was in every
session's context, and one session opened a memory note about the neighbouring bytea fix. All four cells had the same
access, so the arm comparison stands, but "the model knew PostgreSQL 19 rejects the setting" is not evidence of
discovery.

## Results

| Cell | Loaded `test-authoring` | Unit test | Integration test | Red on base (of N tests) | Cost | Turns | Minutes |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A, Opus | yes, unprompted, via the Skill tool | 3 methods added to `V3ParameterListTests` | new class, 3 tests, `SET` on its own connection | 3 of 7 | $5.78 | 56 | 10.3 |
| A, Sonnet | yes, unprompted, via the Skill tool | 3 methods added to `V3ParameterListTests` | 1 method added to the existing simple-mode `PreparedStatementTest` | 3 of 10 | $2.50 | 71 | 9.1 |
| B, Opus | read in step 1 as instructed | 2 parameterized methods, 5 named cases each, in `V3ParameterListTests` | new class, own connection through `options=-c …`, 2 parameterized methods over 4 values plus 2 bytea tests | 9 of 21 | $6.72 | 60 | 13.4 |
| B, Sonnet | read in step 1 as instructed | new class beside `V3ParameterListTests`, 4 methods, fixture duplicated | new class, 2 tests, `assumeTrue` when the server rejects the setting | 5 of 6 | $2.91 | 67 | 12.8 |

Every cell compiled, passed against the fix, and went red with the fix reverted; the reverts were run again here,
outside the sessions. Every cell also reported its own revert run in its final message, which is the skill's §1 rule,
and every cell named the level of each test and why. Checkstyle and autostyle passed in all four.

Question 1 is answered: with the trigger installed, both models loaded the skill before writing and both wrote the
unit test through the public `toString`, which the original pull request did not have. Sonnet in arm A also loaded
`javadoc-authoring` and `english-developer-style` on its own.

Question 2 is answered less firmly:

- Arm B cost 16 percent more in dollars and about a third more wall time for both models.
- Opus with a plan produced the most thorough set: a decision table (setting on and off, times five value classes
  including the trailing-backslash boundary and the `bytea` call site) with every case named by its condition; an
  integration class that configures the server setting through connection options rather than `SET`, so nothing
  leaks to parallel tests; a negative control (`it's`, which never warned); and a separate round-trip test it
  explicitly labelled as green on the base commit and there to catch a fix that removes the warning by breaking the
  value. It also found, in step 1, that `PGbytea.toPGLiteral` writes the hex form as a plain literal under the same
  setting, which is a real defect the maintainer had fixed in a neighbouring open pull request.
- Sonnet with a plan was not better than Sonnet without one. Its plan said to put the unit test beside
  `V3ParameterListTests`; the code created a second class in the same package with the fixture copied, which §9 of
  the skill forbids, and the plan's `PreparedStatementTest` option became a new class as well. Its step-1 reply
  ended by asking for confirmation before writing, which the harness ignored.
- Opus without a plan covered the same three unit shapes as arm B's Opus without the decision table, and reported
  three hand-made mutations (revert the prefix, stop doubling the backslash, remove the `bytea` branch) with which
  test each one turned red, which no other cell did.

So the plan step paid for itself with Opus and not with Sonnet, on one run each. What the plan step visibly changed
was input selection: the two-axis table and the named boundary appeared only where the model had written the
partition list down before coding.

## What the trial says about the skill

- The trigger paragraph is enough for both models to load the skill without being told; the earlier pull request,
  written before the skill existed, is the control.
- §5's "read the value back through the public API" and §3's level table were followed by all four; every cell
  tested `quoteAndCast` through `toString` rather than by reflection.
- §7's report rules were followed unevenly: every cell used `assertEquals` and `assertNull`, and every failure
  printed the operands, but two cells left `assertTrue(rs.next())` without a message, and one put the scenario into
  a message the name already carried.
- §9's placement rule lost once (B, Sonnet). The rule is stated; the plan step did not make it stick.

Three answers follow.

**What the new skill settles.** The one finding the review said it "would actually push on", the missing unit test,
did not occur in any cell: all four wrote it, through the public `toString`, and the two Opus cells also showed which
production change turns it red. The `assertTrue(a == b)` finding did not occur either, because no cell wrote a boolean
assertion around a comparison. Both are the skill's rules (§3 and §7), and both are also the two findings the original
pull request drew that a maintainer would have to act on rather than reword.

**What the review found that the skill does not address.** Everything about prose, which is by design: the class
comment's shape, the pronouns, "shape" as a noun, the list without semicolons, the three copies of one explanation
belong to `javadoc-authoring`, `english-developer-style`, and `change-description-authoring`, and the trial shows those
findings recurring in the cells that wrote a class comment. One of them is a live conflict rather than a gap:
`javadoc-authoring` tells a test class to open with the firing condition ("Fails when …"), the review objects to
exactly that form as a negation the reader has to unpack, and three of the four cells followed the skill. That is a
decision for `javadoc-authoring`, not for this skill. The other findings the skill does not address are about the
change, not the test: the three sibling call sites with the same defect, and the `toString()` rendering context. No
cell found the three sites; one plan-first cell found the `toString()` point and a different neighbouring defect. A
rule that says "grep for the pattern you just fixed" would belong to a change-authoring skill, and none exists.

**What got worse.** Two things, both in the cells that added a class rather than a method. The original pull request
had one test class with a table and five methods; three cells produced a second explanatory class comment that
restates the fix's mechanism, which is the "three copies" finding again with one more copy. And one cell (B, Sonnet)
duplicated the fixture of the existing unit test class instead of extending it, which the original did not do because
it had no unit test at all. Neither is caused by a rule of `test-authoring`; the first is the doc-comment skill's
"Summary = the firing condition" applied to a class that did not need a paragraph after it, and the second is §9 of
this skill not being followed.
