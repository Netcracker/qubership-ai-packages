# Trial on pgjdbc pull request 2837

The skill tried on a real change before it was called done: a review of
[pgjdbc/pgjdbc#2837](https://github.com/pgjdbc/pgjdbc/pull/2837), which adds one `FINE` log statement to the driver's
adaptive-fetch path. Two headless Opus runs, `claude -p --setting-sources project`, took the same prompt
(`prompt_ab-pr2837.md`) over the same fixture: the diff and the two files it touches. One run had the skill installed
as a project skill, the other had none, and neither prompt names the skill.

## Loading

The run with the skill invoked `telemetry-authoring` unprompted, then read `references/jvm.md` and no other reference
file. `claude -p` without `--output-format stream-json` prints only the final text, so the load was confirmed from the
session transcript rather than from the run log.

## The fixture gave both runs too much

The prompt lists the connection properties by name, quotes an existing `FINEST` line that already prints the applied
fetch size, and repeats the pull request author's own hypothesis. Two findings reached both runs almost complete, so
the number of findings each run reported establishes nothing. The comparison below is limited to what the runs did
differently in kind. A re-run needs a prompt with the bare diff and the sources only.

## What both runs found

- The numbers print through `java.text.MessageFormat`, so they come out grouped by the locale.
- `query.hashCode()` is an identity hash, while the cache is keyed by the SQL text.
- The message names private fields instead of the connection properties a user sets.
- The record does not show whether the computed size was clamped.
- The first record reads `from -1`, which looks like a real previous size.
- The exception the author was chasing carries no adaptive-fetch context.

The run without the skill also concluded on its own that attaching the values to the exception mattered more than
the log line.

## What only the run with the skill found

- **A defect in the driver rather than in the logging.** When one row is larger than `maxResultBuffer`, the integer
  division yields `0`, and the default `adaptiveFetchMinimum` of `0` leaves it there. `PgResultSet` replaces the fetch
  size only when the adaptive value is not `-1`, and `QueryExecutorImpl` uses a portal only when `fetchSize > 0`, so
  an adaptive size of `0` fetches every row. The orchestrator checked both call sites against the driver's master
  branch after the run.
- **`-1` has three meanings in one line**: no adaptive size yet, `adaptiveFetchMaximum` unset, and the value
  `getFetchSizeForQuery` returns when adaptive fetch does not apply.
- **The existing guard is correct once the branch is named.** `newFetchSize != previousFetchSize` emits one record
  when the clamp starts to apply and nothing while it holds, which is the transition rule. The run without the skill
  proposed a record on every increase of the largest row size.
- **The checklist answered every item**, including `none` for configuration, log-and-rethrow, threshold, span, and
  context, and recorded that the buffer overflow correctly stays on the caller's channel.
