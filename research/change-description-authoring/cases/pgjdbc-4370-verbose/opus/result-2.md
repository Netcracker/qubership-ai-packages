`VisibleBufferedInputStream` reads throw a `SocketTimeoutException` from the wrapped stream only when the caller requested the timeout through `PGStream.setNetworkTimeout`. The `socketTimeout` connection property and `Connection.setNetworkTimeout` both request it that way. Otherwise `ensureBytes` waits the timeout out. `skip` did not follow that rule. Once its buffer was empty, it called the wrapped stream's `skip`, which reads on a JDK socket stream, and the timeout reached the caller.

The driver also sets a socket timeout without requesting it. [`V3ReplicationProtocol.configureSocketTimeout`](https://github.com/pgjdbc/pgjdbc/blob/f171cd8af6fc5f341c765309af0c1ab0db6fbfb7/pgjdbc/src/main/java/org/postgresql/core/v3/replication/V3ReplicationProtocol.java#L121-L142) sets it to the replication status interval and leaves it on the connection. The interval is 10 seconds unless the caller passes another value to `withStatusInterval`. With `socketTimeout` at its default of 0, discarding the rest of a message on that connection threw `java.net.SocketTimeoutException: Read timed out` if none of its bytes arrived within the interval. A read in the same place would have waited. `PGStream.skip` discards through `VisibleBufferedInputStream.skip` in two cases: a message that `QueryExecutorImpl.skipMessage` ignores, and a field that `receiveTupleV3` could not allocate. The discard also depended on how a stream supplied through `socketFactory` implements `skip`, and such a stream may skip nothing while data is still coming. #4358 compensated with a loop in `PGStream.skip`.

`VisibleBufferedInputStream.skip` now takes what the buffer holds. When the buffer is empty, it calls `read()`, which refills it through `ensureBytes` and so handles a timeout like any other read. It never calls the wrapped stream's `skip`, and it never grows the buffer. It returns less than `n` only at end of stream, so `PGStream.skip` drops the #4358 loop and throws `EOFException` on a short count. The unreleased #4358 changelog entry said that the driver used to mistake a stream that skips nothing for one that has ended. In fact the loop before #4358, `s += pgInput.skip(size - s)`, looped forever on such a stream.

A count of zero or less now discards nothing and returns 0. Before, a negative count was returned as the number discarded, and a negative count within the `int` range moved the read position back. After one byte was read, `skip(-2)` moved the position below the start of the buffer, and the next read threw `ArrayIndexOutOfBoundsException`. The #4358 loop never passed a negative count, but the single call that replaces it passes whatever size `PGStream.skip` receives.

Catching the timeout around the wrapped `skip` would not work. `InputStream.skip` discards the bytes it read before the exception without reporting how many, so a retry cannot tell how many are left. A discard through the buffer that a requested timeout interrupts loses its count the same way, so it cannot be restarted either. Reading through the 8192-byte buffer is also faster. From Java 13 on, the JDK socket stream inherits `InputStream.skip`, which reads 2048 bytes at a time. Over a loopback socket, discarding 256 MiB took 75 ms, against 149 ms with the old `skip`.

`VisibleBufferedInputStreamSkipTest` has 15 cases, and 10 of them also pass against the old `skip`. The 5 that fail cover the unrequested timeout, the counts -1, -2, and `Long.MIN_VALUE`, and the stream that skips nothing. `PGStreamSkipTest` drops `skipDoesNotFallBackToReadingByteByByte` and the cases for streams that skip fully or one byte per call, because the wrapped `skip` is no longer called. No test now limits how many reads a long discard makes.

**Scope.** Neither #4359 nor #4360 is a dependency. All three pull requests add a `CHANGELOG.md` bullet directly above the #4358 entry, and this branch rewrites that entry. #4359 adds the same `if (n <= 0) { return 0; }` guard and also creates `VisibleBufferedInputStreamSkipTest.java`. This branch carries the `-2` case from #4359 too. #4360 changes `readMore` and `read(byte[],int,int)` in `VisibleBufferedInputStream`, but not `skip`.
