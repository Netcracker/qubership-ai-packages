With `socketTimeout` at 0, the default, discarding the rest of a message on a replication connection threw `java.net.SocketTimeoutException: Read timed out` when none of its bytes arrived within the status interval. A read would have waited instead. [`V3ReplicationProtocol.configureSocketTimeout`](https://github.com/pgjdbc/pgjdbc/blob/f171cd8af6fc5f341c765309af0c1ab0db6fbfb7/pgjdbc/src/main/java/org/postgresql/core/v3/replication/V3ReplicationProtocol.java#L121-L142) sets the socket timeout to that interval and leaves it on the connection. The interval is 10 seconds unless the caller passes another value to `withStatusInterval`. Reads in `VisibleBufferedInputStream` wait out such a timeout in `ensureBytes`. They throw it only when the caller requested it through `PGStream.setNetworkTimeout`, as the `socketTimeout` connection property and `Connection.setNetworkTimeout` do. `skip` called the wrapped stream's `skip` once its buffer was empty. On a JDK socket stream that call reads, so the timeout reached the caller. `PGStream.skip` discards this way for a message that `QueryExecutorImpl.skipMessage` ignores and for a field that `receiveTupleV3` could not allocate. The discard also depended on how a stream supplied through `socketFactory` implements `skip`, which may skip nothing while data is still coming. #4358 compensated with a loop in `PGStream.skip`.

`VisibleBufferedInputStream.skip` now takes what the buffer holds. When the buffer is empty, it calls `read()`, so a timeout is handled the same way as in any other read. It never calls the wrapped stream's `skip`, and it never grows the buffer. It returns less than `n` only at end of stream, so `PGStream.skip` drops the #4358 loop and throws `EOFException` on a short count. A count of zero or less now discards nothing and returns 0. Before, a negative count was returned as the number discarded, and one within the `int` range moved the read position back. After one byte was read, `skip(-2)` moved it below the start of the buffer, and the next read threw `ArrayIndexOutOfBoundsException`. The #4358 loop never passed such a count, but the single call that replaces it passes whatever size `PGStream.skip` receives.

Catching the timeout around the wrapped `skip` would not work. `InputStream.skip` discards the bytes it read before the exception without reporting how many, so a retry cannot tell how many are left. A discard through the buffer that a requested timeout interrupts loses its count in the same way, and it can't be restarted either. From Java 13 on, the JDK socket stream inherits `InputStream.skip`, which reads 2048 bytes at a time. Reading through the 8192-byte buffer is faster: discarding 256 MiB over a loopback socket took 75 ms, against 149 ms with the old `skip`.

The unreleased #4358 changelog entry described that loop. It also said the driver used to mistake a stream that skips nothing for one that has ended. In fact, the loop before #4358, `s += pgInput.skip(size - s)`, looped forever on such a stream. The entry now names the two hangs #4358 fixed and the `EOFException`.

`PGStreamSkipTest` drops two kinds of test because the wrapped `skip` is no longer called: the streams that skip fully or one byte per call, and `skipDoesNotFallBackToReadingByteByByte`. No test now limits how many reads a long discard makes.

**Scope.** Neither open sibling is a dependency. All three pull requests add a `CHANGELOG.md` bullet directly above the #4358 entry, which this branch rewrites.

* #4359 adds the same `if (n <= 0) { return 0; }` guard and also creates `VisibleBufferedInputStreamSkipTest.java`. This branch carries its `-2` case.
* #4360 changes `readMore` and `read(byte[],int,int)`, not `skip`.
