With `socketTimeout` at 0, the default, discarding the rest of a message on a replication connection threw `java.net.SocketTimeoutException: Read timed out` if no byte of it arrived within the status interval. A read in the same situation would have waited. [`V3ReplicationProtocol.configureSocketTimeout`](https://github.com/pgjdbc/pgjdbc/blob/f171cd8af6fc5f341c765309af0c1ab0db6fbfb7/pgjdbc/src/main/java/org/postgresql/core/v3/replication/V3ReplicationProtocol.java#L121-L142) sets the socket timeout to that interval and leaves it on the connection. The interval is 10 seconds unless the caller passes another value to `withStatusInterval`. Reads in `VisibleBufferedInputStream` throw a `SocketTimeoutException` from the wrapped stream only when the caller requested the timeout through `PGStream.setNetworkTimeout`, as `socketTimeout` and `Connection.setNetworkTimeout` do. Otherwise `ensureBytes` waits it out. [`skip`](https://github.com/pgjdbc/pgjdbc/blob/f171cd8af6fc5f341c765309af0c1ab0db6fbfb7/pgjdbc/src/main/java/org/postgresql/core/VisibleBufferedInputStream.java#L302-L314) did not follow that rule. Once its buffer was empty, it called the wrapped stream's `skip`, which reads on a JDK socket stream, and the timeout reached the caller. [`PGStream.skip`](https://github.com/pgjdbc/pgjdbc/blob/f171cd8af6fc5f341c765309af0c1ab0db6fbfb7/pgjdbc/src/main/java/org/postgresql/core/PGStream.java#L679-L699) discards this way for a message that `QueryExecutorImpl.skipMessage` ignores and for a field that `receiveTupleV3` could not allocate. The discard also depended on the `skip` of a stream supplied through `socketFactory`, which may skip nothing while data is still coming. #4358 compensated with a loop in `PGStream.skip`.

`VisibleBufferedInputStream.skip` now takes what the buffer holds. When the buffer is empty, it calls `read()`, which refills it through `ensureBytes` and so handles a timeout the same way. It never calls the wrapped stream's `skip`, and it never grows the buffer. It returns less than `n` only at end of stream, so `PGStream.skip` drops the #4358 loop and throws `EOFException` on a short count. A count of zero or less now discards nothing and returns 0. Before, a negative count was returned as the number discarded, and one within the `int` range moved the read position back. After one byte was read, `skip(-2)` moved it below the start of the buffer, and the next read threw `ArrayIndexOutOfBoundsException`. The #4358 loop never passed a negative count, but the single call that replaces it passes whatever size `PGStream.skip` receives.

Catching the timeout around the wrapped `skip` would not work. `InputStream.skip` discards the bytes it read before the exception without reporting how many, so a retry cannot tell how many are left. A discard through the buffer that throws part-way on a requested timeout loses its count the same way, so it cannot be restarted either. From Java 13 on, the JDK socket stream inherits `InputStream.skip`, which reads 2048 bytes at a time. Reading through the 8192-byte buffer discarded 256 MiB over a loopback socket in 75 ms, against 149 ms with the old `skip`.

The unreleased #4358 changelog entry described the loop. It also said that the driver used to mistake a stream that skips nothing for one that has ended. In fact, the loop before #4358, `s += pgInput.skip(size - s)`, looped forever on such a stream. The entry now names the two hangs that #4358 fixed and the `EOFException`.

`PGStreamSkipTest` now runs over a source whose `skip` returns 0. It drops the streams that skip fully and one byte per call, because the wrapped `skip` is no longer called. It also drops `skipDoesNotFallBackToReadingByteByByte`, so no test limits how many reads a long discard makes. Against the old `skip`, 5 of the 15 cases in `VisibleBufferedInputStreamSkipTest` fail: the unrequested timeout, the counts -1, -2, and `Long.MIN_VALUE`, and the stream that skips nothing.
