This change updates `TESTING.md` and the pull request template, and both describe a test setup the repository no longer has. `TESTING.md` says most tests are JUnit 4 and tells you to add a test class to a suite. The template asks whether new test classes go into a suite in alphabetical order. But no file under `pgjdbc/src/test` imports `org.junit.Test`, `org.junit.Assert`, or `org.junit.runner`, and Gradle finds test classes without a suite class.

In section 5 of `TESTING.md`, new tests now use JUnit 5 and go under `pgjdbc/src/test/java/org/postgresql`. Two modules keep JUnit 4 because they need a JUnit 4 runner. `pgjdbc-junit4-test` holds the class-unloading test, which needs the JUnit 4 runner of the classloader-leak-test library. `pgjdbc-osgi-test` holds the OSGi tests, which run on Pax Exam. Add a test to one of those modules only when it needs that runner. The build enforces this: at the merge base, lines 157 to 162 of `pgjdbc/build.gradle.kts` reject `junit:junit` on the test compile classpath, so a JUnit 4 test under `pgjdbc` does not compile. Section 6 now shows JUnit 5 `Assertions` examples in place of the JUnit 4 `Assert` ones.

The template asked about tests in both "New Feature Submissions" and "Changes to Existing Features". Those items are now one "Tests and style" section. It asks whether your changes are covered by tests, whether a bug fix's new test fails without the fix, whether the tests pass locally, and whether `./gradlew styleCheck` passes. The item about explaining what your changes do moves to "All Submissions", because every pull request needs it. The "Does this break existing behaviour?" question stays under "Changes to Existing Features".

To check the JUnit claim, run `git grep -lE 'org\.junit\.(Test|Assert|runner)' -- pgjdbc/src/test` on `master`. It prints nothing. The same search over the whole repository finds files only under `pgjdbc-junit4-test` and `pgjdbc-osgi-test`.

The change edits documentation and the pull request template only. No test was added or run.
