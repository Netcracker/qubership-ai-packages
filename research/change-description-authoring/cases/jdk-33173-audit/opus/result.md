`JNIHandles::is_same_object` upcalls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call`, using the method from `Universe::is_substitutable_method()`. `JavaCalls::call` runs the pre-resolved method without initializing its holder class. `InterpreterRuntime::is_substitutable` makes the same upcall but calls `method_holder()->initialize(...)` first, and `is_same_object` skips that call. As a result, when `is_same_object` is the first code to use `ValueObjectMethods`, it runs `isSubstitutable` in an uninitialized class.

This change doesn't add another on-demand initialization. Instead, when preview features are enabled, the VM initializes `ValueObjectMethods` at startup in `Threads::initialize_java_lang_classes`, right after `UnsafeConstants` and before `System.initPhase1()`. Every upcall now relies on that, so the interpreter, `JVM_IHashCode`, and the C2 path in `SharedRuntime::find_callee_info_helper` no longer initialize the class themselves, and `jniHandles.cpp` is unchanged.

`Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` now assert that the class is initialized. In a debug build, JDK code that compares value objects or computes their hash codes before the class is initialized fails with `value object comparison occurring too early` or `value object hashcode occurring too early`. Before this change, the class was initialized lazily at that point, which is a bootstrapping bug that went unnoticed. `Runtime1::substitutability_check` used to call `JavaCalls::call_static` by name and signature, which initialized the class as a side effect of resolution. It now takes the method from `Universe::is_substitutable_method()` like the other sites, so the assert covers C1 too.

Before `initPhase1()` the system properties are not set up, and the static initializer of `ValueObjectMethods` read `value.bsm.debug` to set `VERBOSE`. Running it that early therefore threw `NullPointerException`. `VERBOSE` is now the constant `false`, so `-Dvalue.bsm.debug=true` no longer turns on debug output. The flag stays because turning debug output on still takes a one-line edit instead of adding the logging code back.

Once `VERBOSE` no longer reads a property, `jdk.internal.misc.Unsafe` is the only class `ValueObjectMethods` needs. `Unsafe` is now initialized before `initPhase1()` rather than during it, where it was a dependency of `LazyConstantImpl` through `SystemProps` and `Charset`. Without `--enable-preview` the startup sequence is unchanged.

No test is added: in debug builds the new asserts check every upcall. I ran these locally: all Valhalla tests, tiers 1 to 3, and the `--enable-preview` subset of tier 7.
