`JNIHandles::is_same_object` upcalls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call`, using the method from `Universe::is_substitutable_method()`. `JavaCalls::call` runs the pre-resolved method without initializing its holder class. `InterpreterRuntime::is_substitutable` makes the same upcall but calls `method_holder()->initialize(...)` first, and `is_same_object` does not. The upcall runs without the initialization when `is_same_object` is the first code to compare value objects. [JDK-8391022](https://bugs.openjdk.org/browse/JDK-8391022) fixed the same missing initialization in `JVM_IHashCode`.

This change does not add one more on-demand initialization. When preview features are enabled, the VM now initializes `ValueObjectMethods` at startup, right after `UnsafeConstants` and before `System.initPhase1()`. No upcall site then needs an initialization of its own, so `jniHandles.cpp` is unchanged. Initializing the class right after `initPhase1()` would not help Java code that runs before that point, because a lazy initialization there is the same bootstrapping problem. `Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` now assert that the class is initialized. A use before startup initialization therefore fails reliably in a debug build, with `value object comparison occurring too early` or `value object hashcode occurring too early`. Without preview features the startup sequence is unchanged.

Running the initialization before `initPhase1()` required three more changes:

- The static initializer read the system property `value.bsm.debug` to set `VERBOSE`. System properties are not set up before `initPhase1()`, so the read threw `NullPointerException`. The property no longer has any effect, and `VERBOSE` is the constant `false`. `VERBOSE` stays instead of being removed: to get debug output, you change one line instead of adding the logging code back.
- `jdk.internal.misc.Unsafe` is now initialized earlier, because it is the only prerequisite `ValueObjectMethods` has left. Until now, `initPhase1()` initialized `Unsafe` as a dependency of `LazyConstantImpl`, which `Charset` uses, which `SystemProps` uses.
- `Runtime1::substitutability_check` called `JavaCalls::call_static` with the class, method name, and signature. That call resolved the method again and initialized the class as a side effect of resolution. It now takes the method from `Universe::is_substitutable_method()` like the other sites, so the new assert covers the C1 upcall too.

There is no new test, because the new asserts check every upcall in debug builds. I ran all Valhalla tests, tiers 1 to 3, and the `--enable-preview` subset of tier 7 locally.
