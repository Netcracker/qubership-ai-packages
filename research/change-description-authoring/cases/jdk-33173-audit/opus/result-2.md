`JNIHandles::is_same_object` upcalls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call`, using the method from `Universe::is_substitutable_method()`. `JavaCalls::call` runs the pre-resolved method without initializing its holder class. `InterpreterRuntime::is_substitutable` initializes `ValueObjectMethods` before the same upcall, but `is_same_object` does not. So when `is_same_object` makes the first value object comparison, the upcall runs against an uninitialized class. JDK-8391022 fixed the same omission in `JVM_IHashCode`.

This change does not add one more on-demand initialization. When preview features are enabled, it initializes `ValueObjectMethods` at startup instead, in `Threads::initialize_java_lang_classes` right after `UnsafeConstants` and before `System.initPhase1()`. In debug builds, `Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` now assert that the class is initialized. If the class is used too early, they fail with `value object comparison occurring too early` or `value object hashcode occurring too early`. A future bootstrapping bug then fails reliably, where an on-demand initialization would hide it. The class is now initialized from startup, so the on-demand initializations in the interpreter, `JVM_IHashCode`, and the C2 path are no longer needed, and `is_same_object` needs none either. `Runtime1::substitutability_check` resolved the method by name, which initialized the class as a side effect. It now uses the pre-resolved method, as the other sites do.

Before `initPhase1()`, the system properties are not set up. The static initializer read `value.bsm.debug` to set `VERBOSE`, so it threw `NullPointerException` at that point. `VERBOSE` is now the constant `false`, and the `value.bsm.debug` property has no effect. The flag stays so that debug output can be turned on by editing one line. The only prerequisite left is `jdk.internal.misc.Unsafe`, which is therefore initialized earlier than before. Until now it was initialized during `initPhase1()`, as a dependency of `LazyConstantImpl`, which `Charset` uses, which `SystemProps` uses. Without preview features, the startup sequence is unchanged.

Initializing the class right after `initPhase1()` would have kept the property. But Java code that runs before that point and compares value objects would still depend on a lazy initialization. That is the same bootstrapping problem, and with eager initialization the assert reports it.

This change has no new test, because the asserts check every upcall in debug builds. I ran all Valhalla tests, tiers 1 to 3, and the `--enable-preview` subset of tier 7 locally.
