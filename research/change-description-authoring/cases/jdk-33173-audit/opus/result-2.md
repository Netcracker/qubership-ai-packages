JDK-8391022 added the missing initialization of `ValueObjectMethods` before the upcall from `JVM_IHashCode`. After that fix was integrated, an automated audit found one more upcall without the initialization. `JNIHandles::is_same_object` calls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call`, using the method from `Universe::is_substitutable_method()`. `InterpreterRuntime::is_substitutable` makes the same call, but it calls `method_holder()->initialize(...)` first, and `is_same_object` does not. `JavaCalls::call` runs the pre-resolved method without initializing its holder class.

This change does not add one more on-demand initialization. Instead, when preview features are enabled, `ValueObjectMethods` is initialized at startup in `Threads::initialize_java_lang_classes`. This happens right after `UnsafeConstants` and before `System.initPhase1()`. With the class initialized from startup, the on-demand initializations in the interpreter, `JVM_IHashCode`, and the C2 path are removed. `is_same_object` needs no change. `Runtime1::substitutability_check` in C1 resolved the method again by name and signature, and that resolution initialized the class as a side effect. It now takes the method from `Universe::is_substitutable_method()`, as the other sites do. In debug builds, `Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` assert that the class is initialized. They fail with `value object comparison occurring too early` and `value object hashcode occurring too early`.

Initializing the class right after `initPhase1()` would avoid touching its static initializer, and it was the first proposal in the issue discussion. It would still leave Java code that runs before `initPhase1()` and compares value objects. That code has the same bootstrapping problem whether the class is initialized lazily or eagerly. With eager initialization and the asserts, such a use fails reliably instead of being hidden. To run before `initPhase1()`, the static initializer no longer reads the `value.bsm.debug` system property, because the system properties are not set up at that point and the read threw `NullPointerException`. In review, someone asked whether `VERBOSE` should be removed. It stays, defaulting to `false`, so debug output can be turned on by changing one line instead of adding the logging code back. The class now depends only on `jdk.internal.misc.Unsafe`, which is therefore initialized earlier than before. Until now, `Unsafe` was initialized during `initPhase1()` as a dependency of `LazyConstantImpl`, which `Charset` uses, which `SystemProps` uses.

User-visible changes:
- The `value.bsm.debug` system property is no longer read. `VERBOSE` in `ValueObjectMethods` is the constant `false`.
- Not changed: without preview features enabled, the startup initialization sequence is the same as before.

There is no new test because the new asserts check every upcall in debug builds. I ran all Valhalla tests locally, tiers 1 to 3, and the `--enable-preview` subset of tier 7.
