`JNIHandles::is_same_object` upcalls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call`, with the method from `Universe::is_substitutable_method()`. `JavaCalls::call` runs a pre-resolved method without initializing its holder class. `InterpreterRuntime::is_substitutable` initializes `ValueObjectMethods` before the same upcall, but `is_same_object` does not. A JNI caller can therefore reach `is_same_object` before anything else has initialized the class, and `isSubstitutable` then runs in an uninitialized class. [JDK-8391022](https://bugs.openjdk.org/browse/JDK-8391022) fixed the same gap in `JVM_IHashCode`.

This change initializes `ValueObjectMethods` once at startup, so no call site needs its own on-demand initialization. When preview features are enabled, `Threads::initialize_java_lang_classes` initializes the class right after `UnsafeConstants`, before `System.initPhase1()`. `Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` now assert that the class is initialized. In a debug build, a use before startup initialization fails with `value object comparison occurring too early` or `value object hashcode occurring too early`, so the bootstrapping bug shows up instead of staying hidden. With the class initialized at startup, the interpreter, `JVM_IHashCode`, and the C2 path no longer initialize it themselves, and `jniHandles.cpp` is unchanged. `Runtime1::substitutability_check` in C1 used to resolve `isSubstitutable` by name and signature, which initialized the class as a side effect. It now takes the method from `Universe::is_substitutable_method()` like the other sites, so the assert covers C1 too.

Before this change, the static initializer could not run before `initPhase1()`. It read the system property `value.bsm.debug` to set `VERBOSE`, and the system properties are not set up at that point, so it threw `NullPointerException`. `VERBOSE` is now the constant `false`, and `value.bsm.debug` is no longer read. `VERBOSE` stays so that debug output can be turned back on by changing one line, without adding the logging code back. With the property gone, `jdk.internal.misc.Unsafe` is the only class `ValueObjectMethods` needs. `Unsafe` used to be initialized during `initPhase1()`: `SystemProps` uses `Charset`, which uses `LazyConstantImpl`, which depends on `Unsafe`. With preview enabled, `Unsafe` is now initialized earlier, before `initPhase1()`. Without preview, the startup sequence is unchanged.

There is no new test because the new asserts check every upcall in debug builds. I ran all Valhalla tests, tiers 1 to 3, and the `--enable-preview` subset of tier 7 locally.
