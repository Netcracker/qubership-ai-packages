An automated post-integration audit of [JDK-8391022](https://bugs.openjdk.org/browse/JDK-8391022), which fixed a missing initialization of `ValueObjectMethods` before an upcall from `JVM_IHashCode`, found one more upcall without it: `JNIHandles::is_same_object`. It calls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call` with the method from `Universe::is_substitutable_method()`. Unlike `InterpreterRuntime::is_substitutable`, it does not call `method_holder()->initialize(...)` first, and `JavaCalls::call` runs a pre-resolved method without initializing its holder class. No failure has been reported, and what a JNI caller would observe if it ran first has not been worked out.

This change initializes `ValueObjectMethods` at startup instead. When Valhalla preview is enabled, `Threads::initialize_java_lang_classes` initializes it right after `UnsafeConstants`, before `initPhase1()`. The upcall sites then need no initialization of their own, and `JNIHandles::is_same_object` needs no call either. Without preview, the sequence is unchanged. Before this change the class could not be initialized that early. Its static initializer read `value.bsm.debug` to set `VERBOSE`, system properties are not set up before `initPhase1()`, and the initializer threw `NullPointerException`. `VERBOSE` is now the constant `false`, and the class comment says the class is initialized very early and must keep minimal dependencies. `Unsafe` is now initialized earlier as well. It is the only prerequisite left, and before this change it was initialized during `initPhase1()`, as a dependency of `LazyConstantImpl`, which `Charset` and `SystemProps` use.

The first option considered was to initialize the class right after `initPhase1()`. That would leave Java code that runs earlier free to start a value object comparison, which more of the JDK may do as it adopts value classes. Eager initialization exposes such bugs instead of hiding them. A reviewer pointed out that lazy initialization before `initPhase1()` raises the same bootstrapping problem, and that a check which fails reliably when the class is used too early exposes future bootstrapping bugs. The `initialize` calls are removed from `InterpreterRuntime::is_substitutable`, `JVM_IHashCode`, and `SharedRuntime::find_callee_info_helper`. `Runtime1::substitutability_check` called `JavaCalls::call_static`, which resolved the method by name and initialized the class as a side effect. It now takes the method from `Universe::is_substitutable_method()`, as the other sites do.

User-visible change: the system property `value.bsm.debug` is no longer read, so setting it has no effect. Debug output is now turned on by changing `VERBOSE` in `ValueObjectMethods.java` and recompiling. A reviewer asked whether `VERBOSE` should be removed altogether, since turning it on already means editing the source. It stays, defaulting to `false`, because enabling debug output then takes one changed line rather than adding the logging code back.

No test is new. The asserts in `Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` check every upcall in debug builds. They fail with `value object comparison occurring too early` and `value object hashcode occurring too early` when the class is not yet initialized. I ran all Valhalla tests locally, tiers 1 to 3, and the `--enable-preview` subset of tier 7.
