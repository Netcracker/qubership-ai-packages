`JNIHandles::is_same_object` upcalls `ValueObjectMethods.isSubstitutable` with the method from `Universe::is_substitutable_method()`, through `JavaCalls::call`. That call runs the method without initializing its holder class. `InterpreterRuntime::is_substitutable` initializes the class first, and `is_same_object` does not. If the first use of `ValueObjectMethods` comes through `is_same_object`, the upcall runs against an uninitialized class. JDK-8391022 fixed the same missing initialization for the upcall from `JVM_IHashCode`. This is the same defect at another site.

The fix initializes `ValueObjectMethods` once at startup, so no upcall needs to. With preview features enabled, `Threads::initialize_java_lang_classes` initializes it right after `UnsafeConstants` and before `initPhase1()`. Without preview the sequence is unchanged. `jniHandles.cpp` therefore needs no change. The `initialize` calls in `InterpreterRuntime::is_substitutable`, `JVM_IHashCode`, and `SharedRuntime::find_callee_info_helper` are removed. `Runtime1::substitutability_check` now takes its method from `Universe::is_substitutable_method()` and calls `JavaCalls::call`, as the other sites do. Its previous `JavaCalls::call_static` resolved the method by name and initialized the class as a side effect. In debug builds, `Universe::is_substitutable_method()` and `Universe::value_object_hash_code_method()` assert that the class is initialized, so every upcall through them is checked.

Eager initialization before `initPhase1()` needs `VERBOSE` to stop reading `value.bsm.debug`. System properties are not set up at that point, and the static initializer threw `NullPointerException`. `VERBOSE` is now `false`, and debug output is turned on by changing that one line. `Unsafe` is now the only prerequisite, and it is initialized before `initPhase1()` rather than during it, through `LazyConstantImpl`, `Charset`, and `SystemProps`. The class comment now says it is initialized very early and must keep minimal dependencies. Lazy initialization keeps the same bootstrapping problem. Eager initialization makes a use before initialization fail reliably in debug builds, which exposes later bootstrapping bugs instead of hiding them. Initializing after `initPhase1()` would leave earlier Java code free to compare value objects while the class is uninitialized.

The change adds no test: the new asserts check every upcall in debug builds. I ran all Valhalla tests locally, tiers 1 to 3, and the `--enable-preview` subset of tier 7. What a JNI caller observes when `is_same_object` runs first is not established here, because the change removes that order.
