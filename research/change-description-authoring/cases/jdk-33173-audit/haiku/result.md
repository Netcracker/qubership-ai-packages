`JNIHandles::is_same_object` upcalls `ValueObjectMethods.isSubstitutable` through `JavaCalls::call`, using the method that `Universe::is_substitutable_method()` returns. `JavaCalls::call` runs that method without initializing its holder class. `InterpreterRuntime::is_substitutable` initializes the holder before the same upcall, and so does `JVM_IHashCode`, where [JDK-8391022](https://bugs.openjdk.org/browse/JDK-8391022) added the call. `is_same_object` has no such call. When a JNI caller reaches it before anything else has initialized `ValueObjectMethods`, the upcall runs on an uninitialized class.

This change initializes `ValueObjectMethods` at startup when preview features are enabled. `Threads::initialize_java_lang_classes` does it right after `UnsafeConstants`, before `initPhase1()`. Without preview, the startup sequence is unchanged. Because the class is initialized there, the per-site initialize calls are removed. Two alternatives were rejected. Adding a call at each upcall site leaves every new upcall to remember one, and this upcall lacks one. Initializing the class after `initPhase1()` leaves Java code that runs before that point able to compare value objects while the class is uninitialized. With eager initialization, use before initialization fails an assertion in debug builds, in `Universe::is_substitutable_method()` or `Universe::value_object_hash_code_method()`, with the messages `value object comparison occurring too early` or `value object hashcode occurring too early`.

`VERBOSE` used to read the `value.bsm.debug` system property in the static initializer of `ValueObjectMethods`. System properties are not set up before `initPhase1()`, so initializing the class there threw `NullPointerException`. `VERBOSE` is now the constant `false`. It stays in the source, so turning on debug output means changing one line rather than restoring the logging code. Once `VERBOSE` stops reading a property, `jdk.internal.misc.Unsafe` is the class's only prerequisite. `initPhase1()` used to initialize `Unsafe` as a dependency of `LazyConstantImpl`. With preview enabled, it now initializes earlier.

`JNIHandles::is_same_object` is not changed: with preview enabled, the class is initialized at startup, so the call needs nothing more. `Runtime1::substitutability_check` no longer initializes the class as a side effect of resolving the method through `JavaCalls::call_static`. It takes the method from `Universe::is_substitutable_method()`, as the other upcalls do. The initialize calls in `InterpreterRuntime::is_substitutable`, `JVM_IHashCode`, and the C2 path in `SharedRuntime::find_callee_info_helper` are removed for the same reason.

No test is added. The new assertions check every upcall, but only in debug builds. I ran all Valhalla tests locally, tiers 1 to 3, and the `--enable-preview` subset of tier 7.
