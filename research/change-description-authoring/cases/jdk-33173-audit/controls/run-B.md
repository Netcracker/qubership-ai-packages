After JDK-8391022, an audit of the VM upcalls into `ValueObjectMethods` found one more that does not initialize the class first. `JNIHandles::is_same_object` calls `isSubstitutable` through `JavaCalls::call`, which runs the pre-resolved method without initializing its holder. If JNI `IsSameObject` compares two value objects before anything else has initialized `ValueObjectMethods`, `isSubstitutable` runs with a null `UNSAFE`.

Rather than add the missing call to `is_same_object`, this change initializes `ValueObjectMethods` during VM startup when preview features are enabled, in `Threads::initialize_java_lang_classes` right after `UnsafeConstants`. Patching the one call site leaves the next upcall free to repeat the omission, and initialization on demand had its own limit: before `System.initPhase1` the class initializer threw `NullPointerException`, because `VERBOSE` read the `value.bsm.debug` system property. `VERBOSE` is now the constant `false`, kept as a flag to flip when debugging, so the class depends only on `Unsafe`. That lets it be initialized before `initPhase1` rather than after, because `initPhase1` runs enough Java code that a value object comparison there could appear with any later library change. Without `--enable-preview` the startup sequence is unchanged.

With the class initialized at startup, every upcall takes its `Method*` from `Universe::is_substitutable_method()` or `Universe::value_object_hash_code_method()` and invokes it with `JavaCalls::call`. Both accessors now assert that `ValueObjectMethods` is initialized, so a debug build fails on any comparison or hash code earlier than that point. The per-call-site `initialize()` calls in `InterpreterRuntime::is_substitutable`, `JVM_IHashCode`, and `SharedRuntime::find_callee_info_helper` are removed, and `Runtime1::substitutability_check` moves from `JavaCalls::call_static`, which initialized the class only as a side effect of resolving the method, to the same direct call. The C2 path in `parse2.cpp` needs no change, since the compilers start after `initialize_java_lang_classes`.

`-Dvalue.bsm.debug` no longer enables the `isSubstitutable` trace output; set `VERBOSE` to `true` and rebuild instead.

There is no new test: once the class is initialized at startup, the ordering that exposed `is_same_object` cannot occur, and the new asserts catch a regression in debug builds. Tested with all Valhalla tests locally, tiers 1-3 as a sanity check, and the `--enable-preview` subset of tier 7.
