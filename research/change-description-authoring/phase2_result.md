# Pass 2: Structural Rules for a Change-Description Skill, by Reader

## 1. Executive summary

**Nine of the ten shortlisted candidates survive as rule contributors; only Conventional Commits/release-please drops to background (it is a tooling substrate, not a reader-serving guide).** The rule contributors are: Linux kernel (`submitting-patches`, `stable-kernel-rules`, `Fixes:`/`Link:` trailers — https://www.kernel.org/doc/html/latest/process/submitting-patches.html, https://docs.kernel.org/process/stable-kernel-rules.html), Google eng-practices (https://google.github.io/eng-practices/review/developer/cl-descriptions.html), Tian et al. ICSE 2022 (https://arxiv.org/abs/2202.02974), Li & Ahmed ICSE 2023 (https://stairs.ics.uci.edu/papers/2023/Commit_Messages.pdf), Keep a Changelog + Common Changelog (https://keepachangelog.com/en/1.1.0/, https://common-changelog.org/) with Bi et al. TSE 2022 and Abebe et al. EMSE 2016 supporting, CVE Key Details Phrasing (https://www.cve.org/Resources/General/Key-Details-Phrasing.pdf), Kubernetes (https://www.kubernetes.dev/docs/guide/release-notes/, cherry-picks guide), `git interpret-trailers` + GitHub/GitLab platform mechanics, and PostgreSQL (https://wiki.postgresql.org/wiki/Commit_Message_Guidance, Committing checklist) with Zulip as second rebase source. towncrier/release-please survive only as tooling-design evidence.

**Questions settled vs. open.** Settled: Q1 (issue link vs inline why — Li & Ahmed give the number: ~15% of links fail to deliver Why); Q2 (one `Fixed` entry can serve R3 and R4 if ordered symptom→trigger→fix→compatibility); Q3 (body order: problem-first for commit body and PR, change-first for subject and changelog); Q4 (verification lives in the PR body / kernel `---`, not in `git log`); Q6 (squash mechanics fully documented); Q8 (backporter signals are largely trailers + labels); Q5 (transfer risk assessable per rule). Partly open: Q7 (R3 content is derivable, but no shortlisted project records the *introducing* version in the changelog entry itself — only in trailers/structured fields — and no study measures how operators search release notes; both inferred); Q9 (readers-read-first: only Tao et al. and Bi et al. measure anything; on-call and backporter reading is unstudied); Q10 (Why/rationale has measured support; "scope left out" and "alternatives rejected" are asserted only).

**Most important rule per reader.**
- **R1 (reviewing maintainer):** State what the tests establish and which are new, in the PR body. Reviewing others' changes is the single most frequent change-understanding scenario — Tao et al. (FSE 2012, n=180): *"'Reviewing other's code changes (to give comments or approval for check-in)' received 121 votes (67.2%) and ranked the first."*
- **R2 (archaeologist):** Put a one-line Why plus the greppable identifiers in the commit body, not only behind a link (Tian et al. + Li & Ahmed).
- **R3 (on-call):** Quote the exception class / error text verbatim in the changelog `Fixed` entry and commit body (CVE Key Details Phrasing + kernel dmesg rule + Common Changelog).
- **R4 (upgrading user):** Lead the entry with the observable change and hoist breaking changes to a top block (Keep a Changelog; Bi et al.).
- **R5 (backporter):** Carry a `Fixes:`/`Backpatch-through:` trailer naming the introducing commit or oldest branch (stable-kernel-rules; PostgreSQL).

**Workflow-bound rules and gating.** The skill must detect the merge model *first*. Patch-series rules, the `---` separator, `Cc: stable`, and `Change-Id` are email/Gerrit-bound (high false-positive risk in a squash-merge GitHub repo). The 50-character subject is email-bound; GitHub displays roughly 72 characters before truncation. `/kind` and the fenced `release-note` block are Prow-bound. Gate each rule behind a precondition the agent can test from repo history: does `git log` show `Change-Id:`? do commit subjects end in `(#123)`? does a `CHANGELOG.md` or `changes/` directory exist?

**Split across buckets.** Roughly ~55% agent-skill rules (derivable from diff+tests+issue: write the Why, quote the error text, name new tests, order the entry); ~25% linter/platform checks (subject length, trailer syntax, Conventional Commits prefix, closing-keyword presence, release-note label); ~20% human judgment (severity rating, "is this the ideal solution," what to deliberately leave out, backport go/no-go).

## 6. Worked examples

1. **Rule 2 (inline Why despite a link).** Li & Ahmed's own example (their "Content Repetition" category, 59 of the failing cases): a commit "add @SPI annotation (#6436)" whose linked PR only says "add @SPI annotation to ExtensionFactory #6436." *Before:* subject + bare `#6436`. *After:* add one line — "Needed so third-party factories register without a manual config entry." (Source example is real; the added line is constructed.)
2. **Rule 3 (user-visible impact).** Kernel guidance instructs describing impact, not just the defect. *Before:* "fix off-by-one in ring buffer." *After:* "Under sustained load the ring buffer overran by one entry, corrupting the next slot and producing sporadic `WARN_ON` splats in dmesg." (Constructed to illustrate the kernel rule; the doc states the rule, not this commit.)
3. **Rule 4 (verbatim error text).** Common Changelog's example "Prevent segmentation fault upon `close()`" names the symptom. *Before:* "Fix crash." *After:* "Fix `SIGSEGV` when `close()` is called on an already-closed handle." (CC example extended.)
4. **Rule 14 (lead with observable change).** Bi et al. quote a tester verbatim: *"'Bug fixes and performance improvements' is completely meaningless. What was fixed? How will performance improve?"* *Before:* that phrase. *After:* "Fixed timeouts when exporting datasets larger than 1 GB." (Complaint verbatim; fix constructed.)
5. **Rule 20/21 (squash title/body).** GitHub appends `(#42)` to the squashed subject automatically. *Before title:* "updates." *After title:* "Cache DNS lookups to cut connection setup latency" → becomes subject `Cache DNS lookups… (#42)`, with the PR description as the commit body. (GitHub squash-merge docs — mechanics.)
6. **Rule 27 (Backpatch-through).** PostgreSQL: a fix going into all branches from 15 to master carries `Backpatch-through: 15`. (Verbatim tag definition from the PostgreSQL Commit Message Guidance.)
7. **Rule 29 (fix vs feature).** Kubernetes cherry-pick PRs "are by default expected to be `kind/bug` and `priority/critical-urgent`." *Before:* untyped PR. *After:* `/kind bug`. (Verbatim, Kubernetes cherry-picks doc.)
8. **Rule 31 (affected/fixed versions).** GitHub advisories require an affected version range and a first-patched version. *Before:* "Fixed a security bug." *After:* "Fix path traversal via `../` in upload names; affects 2.0.0–2.3.1, fixed in 2.3.2 (CVE-2025-XXXX)." (Advisory fields real; example constructed.)

## 7. Pitfalls and false positives

- **Rules 5 vs 1 (Google "what first" vs kernel "problem first").** Applying Google's "first line = what" to a subsystem that expects problem-first bug narratives (kernel) makes the subject read as a diff paraphrase; an R2 reader loses the why in the one line most often shown. Resolved in §8 by artifact.
- **Rule 7 (`---` separator) — HIGH.** The `---` convention only strips content under `git am`. In a GitHub squash repo, everything after `---` still lands in the commit body. Following it blindly puts the test plan into `git log` — the exact R2 noise it was meant to prevent.
- **Rule 10 (`Fixes:` trailer) — MEDIUM.** Outside the kernel, `Fixes:` has no standard consumer; some tools treat it as free text. It still helps R5 as prose, but don't assume automation.
- **Rule 20 (PR title → subject) — MEDIUM.** Only true when the repo squash-merges *and* the "PR title" setting is active. In a merge-commit repo the title becomes the merge-commit subject that `git log --first-parent` readers often skip; over-editing then wastes effort.
- **Rule 26 (identical message across branches) — MEDIUM.** Identical messages are what PostgreSQL's `git_changelog` needs, but in a repo whose branches diverge in behaviour, an identical message can misdescribe the back-branch variant. Prefer a one-line branch-specific note.
- **Rule 29 (Conventional Commits type) — MEDIUM/HIGH.** In a repo with no parser, `feat:`/`fix:` prefixes add machine syntax that serves no reader and clutter the subject (Common Changelog's explicit critique).
- **Rules 15/31 (CVE / version ranges) — MEDIUM.** For a project that doesn't issue CVEs, demanding a CVE is a false positive; degrade to "name the advisory or issue."
- **Trivial / under-analyzed:** Rules 8, 17, 25 have weak failure modes — near-universally safe. Flagged as refinements, not load-bearing.

## 8. Conflicts, resolved

**Q1 — Issue link vs inline why.** Tian et al. accepted a link as a proxy for Why; Li & Ahmed measured that ~15% of links fail (content repetition being the largest category, 59 cases), against an 89.77% expectation that the link would add information. **Decision: R2 and R3 win.** The skill writes a one-line Why plus the greppable identifiers into the message and treats the link as supplementary. Minimum inline content when an issue exists: one sentence of rationale + the issue ID + the symptom string. The "losing" party (an author wanting brevity) is not harmed — it is one sentence. Context: Tian et al. found *an average of circa 44%* of messages could be improved, and cite Dyer et al. that ~14% of messages in 23,000+ OSS projects were entirely empty — so the baseline quality problem this rule targets is large.

**Q2 — Who owns `Fixed`: R4 or R3.** One entry can serve both if ordered **symptom (verbatim) → trigger → fix → compatibility/version.** CVE phrasing and Common Changelog lean operator; Keep a Changelog leans user. The order puts R3's greppable symptom first (cheap for R4 to skip) and R4's compatibility statement last. No shortlisted project records the *introducing* version inside the changelog entry itself — the kernel keeps it in `Fixes:`, GitHub advisories keep affected ranges in structured fields — so "introduced-in-changelog" is a recommendation, not observed practice. No study measures how operators search release notes (open).

**Q3 — Problem-first vs change-first.** Kernel orders problem→impact→solution (serves R2/R3). Google puts the *what* on line 1, problem in the body (serves R1 skimming `git log`). Conventional Commits/release-please read only subject + footers. **Resolution by artifact:** commit **subject** = change-first (Google/CC; R2 skimmer wins; the body still carries problem-first); commit **body / PR body** = problem-first (kernel; R2/R1); **changelog entry** = observable-change-first (R4; Bi et al.). Neither reader is harmed because subject and body serve different reading moments.

**Q4 — Verification in the permanent record.** Kernel `---` keeps it out; Google/PR templates include it; squash makes the PR body permanent. **Decision:** "how it was verified" belongs in the PR description's verification section, which in a merge-commit or `---` workflow stays out of `git log`. In a **squash repo it will persist**, so compress it to one line naming what the tests establish (rule 6) and move transcripts/checklists to review comments (rule 22). It does not belong in `git blame`-facing body prose. R1's need is met in the PR; R2's noise is avoided in the log. The agent must detect the merge model; **default when detection fails: treat as squash** (the conservative case — keeps prose short).

**Q5/Q6 — squash mechanics (documented).** GitHub: one commit → squashed subject = that commit's title + PR number, body = that commit's body; multiple commits → subject = PR title + number, body = list of commit messages; maintainers can configure "PR title and description" so the body = the PR description, and can edit before merge. GitLab: squash templates use `%{title}`, `%{issues}`, `%{reference}`; closing patterns in the MR description or a commit close referenced issues on merge to the default branch (configurable, admin-level). **Derived rules for a "title→subject, body→commit-body" repo:** title carries the imperative what (rule 20); body carries problem→why→one-line verification (rule 21); reviewer-only content goes to comments (rule 22, derived); `Closes #` in the description auto-closes on merge to the default branch (documented); `Co-authored-by:` trailers are preserved by both platforms (documented).

**Further conflict — Common Changelog vs Keep a Changelog on Unreleased.** CC drops the Unreleased section (references can only be added after merge); KaC keeps it. Workflow-dependent: if the repo adds entries in-PR, keep Unreleased (KaC); if entries are curated at release from git history, drop it (CC). **Default when undetected: keep Unreleased** (lower coordination cost for contributors).

## 9. Baseline audit

**Commit-message block.**
- *Supported:* "body explains why" (Tian et al., Tao et al. — measured); "reference issues by ID" (GitHub/GitLab mechanics); "don't paraphrase the diff" (Google, Common Changelog).
- *Contradicted:* "`type(scope): summary`, at most 72 characters." Conventional Commits prefixes serve tooling, not readers (Common Changelog's explicit critique) — demote to a conditional linter rule. The 72-char cap conflates workflows: kernel/email wants ~50, PostgreSQL 64, GitHub displays ~72. State it as a platform-detected linter check, not a universal.
- *Neither supported nor contradicted (one team's practice):* nothing material beyond the above.
- *Missing:* the baseline never tells the commit to name the *symptom string* for R3 (rules 3–4) or the introducing commit for R5 (rule 10).

**PR-title block.** Supported and sharpened: "~100 chars, accuracy over brevity, title seeds squash subject, platform appends/strips the number" all match GitHub/GitLab docs. Keep.

**PR-description block (baseline flags Why/What/How-to-verify as weak).** The three-section order is a *reasonable synthesis* but only partly sourced. "Why then What" matches kernel problem-first for the body; the "How to verify" placement is correct (rule 7) but the baseline should add that it must not leak into `git log` on squash (rule 22). The order is **one team's practice, not measured** — Tao et al. supports that rationale is the top need, not the three-header structure. Keep the sections; add the squash caveat; stop implying the order is evidence-based.

**Artifact-level table (baseline flags as unsourced).** Blunt assessment: it asserts each artifact's "level" with no source and partly misassigns. "the changelog = the released, user-visible symptom" is right for R4 but **omits R3's need for the verbatim error string** — the whole point of the CVE/Common-Changelog rules. "the commit message = why, for `git blame` years later" is well-supported (Tao et al., Tian et al.) — keep. "the PR = problem, decision, scope, verification summary" is supported by Google + Tao et al. Re-label the table as an asserted mapping and expand the changelog row to "user-visible change (R4) **and** the greppable symptom (R3)."

**Absence of an R3 rule beyond "name the symptom."** Correctly flagged as thin. Pass 2 adds verbatim error text (4), trigger/workaround (35), affected/fixed versions (31), CVE lead (15) — all **asserted** (CVE/kernel/Common Changelog), not measured. Say so.

**Absence of any R5 rule.** Correctly flagged. Pass 2 adds rules 10, 26–31. Most are trailers/labels; severity (30) and backport go/no-go are human judgment the skill can prompt for but not decide.

**Changelog block.** Supported: six categories, one sentence, link to PR/commit, breaking block on top, "name the symptom even at the cost of a second sentence" (Common Changelog + CVE). This is the best-sourced part of the baseline and survives the audit intact.

## 10. Recommended synthesis

**Slots per artifact, in order, with reader served and the belonging test.**
- **Commit subject** (R2): imperative what-changed; test — does it stand alone in `git log --oneline`? House-style prefix only if a parser exists.
- **Commit body ¶1** (R2/R3): the problem + user-visible impact; test — could an archaeologist reconstruct why without the diff?
- **Commit body ¶2** (R2): why this approach, the constraint that forced it, quantified trade-off; test — does it explain a choice the diff can't?
- **Trailers** (R5/R2/R3): `Fixes:`, `Closes #`, `Backpatch-through:`, `Co-authored-by:`; test — machine-greppable and true?
- **PR title** (R1/R2): searchable, accurate summary (seeds the squash subject).
- **PR body — Why / What / Verify / Scope** (R1): each paragraph must change a review decision; test — which decision gets harder if it disappears?
- **PR body — reviewer-only** (R1, ephemeral): checklists, screenshots, round history → comments; never the description in a squash repo.
- **Changelog entry** (R4+R3): category → observable change → verbatim symptom → reference → compatibility; test — can a user skip it and an operator grep it?

**Greppable trailer/identifier list (single list):** `Fixes: <sha>`; `Closes #n` / `Resolves #n` (default-branch only); `Co-authored-by:`; `Backpatch-through: <ver>`; `Cc: stable # <ver>` (kernel only); CVE/GHSA ID in Security entries; the verbatim exception/error string in body and changelog; the affected/fixed version range.

**Squash-merge repo rules (cited vs derived):** title = imperative subject (cited: GitHub/GitLab docs); PR description = commit body under "title+description" (cited); `Closes #` auto-closes on merge to default branch (cited); `Co-authored-by:` preserved (cited); move checklists/screenshots/test transcripts to comments (derived); compress verification to one line (derived); default to squash assumptions when the model can't be detected (derived).

**Changelog as the R3+R4 shared artifact, order of parts:** `### <category>` → **observable change** (R4) → **verbatim symptom / error string** (R3) → **reference** (commit/PR/CVE) → **compatibility / action required** (R4). Breaking changes hoisted to a top block.

**Anti-patterns each source names, and the reader each fails:** git-log-dump changelog (Common Changelog) → fails R4/R3; content-repetition issue link (Li & Ahmed) → fails R2; "Bug fixes and performance improvements" (Bi et al., verbatim tester complaint) → fails R4/R3; empty/What-only message (Tian et al.) → fails R2; composite/tangled change (Tao et al.) → fails R1/R5; Conventional Commits prefix mistaken for descriptiveness (Common Changelog) → fails R2.

**Load-bearing vs refinement (compression order — drop refinements first):** *Load-bearing:* rules 1, 2, 3, 4, 6, 10, 11, 20, 21, 31. *Refinements (drop first under a budget):* 8, 12, 17, 18, 19, 25, 32, 34.

**Pass 3 synthesis prompt should be told to:** (a) turn these rules into a single skill file with per-rule preconditions the agent can test from repo state; (b) implement merge-model detection first and gate workflow-bound rules; (c) keep the changelog entry order fixed (symptom-greppable). It should be told **not to:** re-derive sentence-level wording (owned by `english-developer-style`); re-open the settled contradictions; treat Conventional Commits / 50-char / `Change-Id` / `Signed-off-by` as reader-serving; or present asserted rules (R3, R5, "scope left out," "alternatives rejected") as measured.
