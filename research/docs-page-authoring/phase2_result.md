# Pass 2: Rules for a Documentation-Page Authoring and Review Skill

## 1. Executive summary

**Rule contributors (survive as sources of applicable rules):** Uddin & Robillard (defect taxonomy + severity), Aghajani et al. (evidence-based issue taxonomy, 162 types), the doctest family (rustdoc/`cargo test --doc`, Python `doctest`, Sphinx directives), RFC 2119/8174 + OASIS (the normative/informative *distinction*, not the uppercase vocabulary), Kubernetes Content/Style Guide (canonical-source and dual-sourcing rules), Keep a Changelog + Common Changelog (entry rules, released-entry handling), purposeful-readme/standard-readme (README scope and ordering), Diátaxis (as a weakened "one primary purpose per section" rule). **Background/supporting:** Meng-Steinhardt-Schubert and Carroll's minimalism inform genre trade-offs but yield few mechanically-checkable rules; the Google structure chapters largely corroborate rules the others state more sharply.

**Questions settled vs. open:** Settled — Q1 (Diátaxis does *not* survive as "one page, one genre"; its own materials concede compound structures), Q2 (version-marker retention: projects do drop old markers, with a concrete CPython/NumPy convention), Q3 (purposeful-readme's rule is defensible as stated with a link exception), Q6 (the *distinction* transfers, not the uppercase MUST), Q9 (released-text immutability is real but analogized, not a formal doc rule). Partially settled — Q5 (tools exist but few are usable/maintained), Q7 (classification is producible; see §3 and the audit). Open — Q4 (intra-doc-set anchor rot is essentially unstudied; the rule is asserted from mechanics, not measured).

**Does the tooling in Q5 exist in usable form?** Partially. Doctest runners are production-grade and belong in CI. Research inconsistency detectors mostly do not: DocRef (2013) detected >1,000 errors on 5 libraries but has no maintained release and no clean precision figure; Fraco is a research Eclipse plugin (~99% precision on Java sets, but not a maintained tool); DocChecker is pip-installable yet its headline 72.3% ICCD accuracy collapses to sub-random precision on the independent CASCADE benchmark; DocPrism (precision 0.62) and CASCADE (precision 0.85) are unreleased 2025–2026 preprints; MPChecker reaches 92.8% recall but only for multi-parameter constraints in Python data-science libraries; the one genuinely usable claim checker is DOCER (outdated code-element references), released as a GitHub Action.

**Three-bucket split:** Most structural constraints (heading skeleton, code-fence integrity, front-matter, link targets) are already enforced by the sweep's oracle and by markdownlint/link-checkers/doctest runners — the agent only reports on them. The agent's real value is the class of defects that require reading the page *and* the source: implementation-stated-as-contract, stale identifiers, unsupported claims, genre drift. That is where a prompt beats a linter.

**Does the Pass 1 four-stage recommendation still hold?** Yes, with one addition: a claim-checking stage keyed to identifiers, because the highest-value defects (incorrectness, outdatedness) are exactly the ones a prose reviewer misses and a source comparison catches.

## 4. Worked examples

1. **Rule 1 (spec not implementation).** The baseline supplies the canonical pair: *before* — "The driver builds a `PreparedStatement` after the fifth execution and caches it on the connection"; *after* — "A statement is prepared on the server after `prepareThreshold` executions. Set `prepareThreshold=0` to disable that." The first sentence can become false under a refactor that no caller notices.

2. **Rule 4 (identifier match).** DOCER's motivating case: google/glog's wiki referenced `DGFLAGS_NAMESPACE` after the symbol was renamed to `DGLOG_GFLAGS_NAMESPACE`; the doc stayed wrong for years until the authors filed issue #750. *Before:* prose names `DGFLAGS_NAMESPACE`. *After:* the current symbol, or the doc is deleted (which is what the maintainer did).

3. **Rule 12 (behavior not diff).** Keep a Changelog's own contrast: *before* — "Fix null ref in ReportFilterService#apply"; *after* — "Fixed a bug where reports failed to load when filtered by date range."

4. **Rule 14 (released entries immutable).** No project states this as a formal doc rule; the closest sourced analogy is release-artifact immutability (GitHub immutable releases, GA October 2025; PyPI file immutability). *Before:* rewording a shipped 1.2.0 entry for tone. *After:* leave it; only correct a factual error.

5. **Rule 15 (README ≠ changelog).** purposeful-readme states verbatim: "The README must not contain a changelog. It may, however, contain a link to CHANGELOG.md." *Before:* a "## Changelog" section in the README. *After:* a one-line link.

6. **Rule 20 (heading as anchor).** *Before:* renaming "## Configuration" to "## Configuring the client" in a wording pass. *After:* keep the heading, or land the rename with a Hugo `aliases`/Docusaurus redirect entry in a separate change. (No doc-set-scale study exists; the rule is from anchor mechanics.)

7. **Rule 27 (normative distinction without MUST).** *Before:* "The client **MUST** retry on 503" with an RFC 2119 boilerplate atop a README. *After:* "The client retries on 503; you can rely on this." Reserve the keyword for a real conformance section, per OASIS's guidance that non-standards notes avoid the keywords.

8. **Rule 28 (marker retention).** NumPy issue #27239 proposes removing `versionadded`/`versionchanged` directives for versions "long out of use" (e.g., ≤1.19) while preserving the current-path information — the concrete retention line. CPython's `versionadded:: next` tooling (gh-121277) shows the same active management from the other end.

## 5. Pitfalls and false positives

- **Rule 2 (history tells) — medium.** Mechanical flagging of "now/previously" breaks on legitimate prose ("the function now returns a list" inside a changelog, or "previously computed value" as a variable description). Restrict the pattern to reference/README bodies and exempt changelog/migration genres.
- **Rule 9 (exhaustiveness) — medium.** Demanding an entry for every public member fights minimalism on a curated "getting started" reference and can force noise for trivial getters. Apply only to pages that declare themselves the reference of record.
- **Rule 12/13 (changelog rules) — medium.** "Every version gets an entry" produces false positives for internal-only releases with no user-visible change; Keep a Changelog itself says skip changes with no user impact. The tag-vs-changelog linter must allow an explicit "no user-visible changes" note.
- **Rule 14 (immutable entries) — medium.** Over-strict application blocks fixing a genuinely wrong or harmful released entry (e.g., a security note with an incorrect CVE). The exception — factual error — must be explicit.
- **Rule 20 (heading rename) — high.** The rule assumes inbound links exist; for a heading this branch introduced, or a site that pins anchors explicitly (`{#id}`, Docusaurus `id:`), rewording is free. Mechanical enforcement on a brand-new page is a pure false positive. This is also the rule with the weakest evidence: intra-doc-set anchor rot is unstudied.
- **Rule 27 (normative marking) — medium.** Flagging all uppercase MUST is wrong inside a genuine spec (an OpenAPI or protocol doc in the repo). Scope the check to READMEs/guides, not `spec/` trees.
- **Rule 31 (config-key existence) — medium.** Dynamic or plugin-provided keys may not appear in a static scan, producing false positives; the check should whitelist documented dynamic namespaces.

Rules 7, 21, 34 have essentially no failure mode because the oracle enforces them by construction — they are not under-analyzed, they are mechanical guarantees the agent restates.

## 6. Conflicts, resolved

**Q1 — Diátaxis vs mixture pages.** Diátaxis asserts (diataxis.fr; Canonical adoption post) that a page "will always be one, and only one, of the four types." But practitioners report content drift, and a real `docs/` tree contains inescapable mixtures — a README is introduction + how-to + reference; a migration guide is how-to + explanation. Diátaxis's own materials concede compound/complex structures and that the compass is "not a cage." **Better supported:** the weakened position. **Skill should say:** replace "one page, one genre" with "one *primary purpose* per section, and no section silently switches purpose." Keep the genre failure-modes (reference drifts into implementation; how-to explains mid-procedure) as detection heuristics, not a taxonomy gate. Default: allow README and migration guides as sanctioned mixtures; flag drift only within a section.

**Q2 — Version markers vs bloat.** Keep a Changelog wants an entry per version; Sphinx/CPython/NumPy maintainers report `versionchanged` accumulation bloats reference pages. These are not truly in conflict — changelogs and reference version-markers are different homes. **Resolution:** the changelog keeps all entries (it is the history of record); the *reference page* drops markers older than the supported window (NumPy #27239; CPython's `next`-expansion tooling shows active management). Default retention line: drop reference markers below the minimum supported version, preserving current-path facts.

**Q3 — purposeful-readme's "no changelog in README."** Defensible as stated: the rationale (duplicate maintenance surface, drift) is sound and the spec already carves the exception (a link is allowed). **Skill should say:** keep the rule; no size threshold needed because the link exception already handles the "small changelog" case. A short "Recent changes" teaser that links out is acceptable; an embedded full changelog is not.

**Q4 — heading rename / anchor rot.** The mechanics are clear and sourced (Hugo `aliases`, Docusaurus `id:`/`slug`, MDN redirect practice, "cool URIs don't change"). But **there is no measurement of intra-doc-set anchor breakage** — the closest studies measure code-element reference rot (DOCER: 28.9% of top-1000 GitHub projects currently carry an outdated reference), not heading-anchor rot. **Honest answer:** the rule is asserted from mechanics, and should be labeled as such in the skill, not presented as evidence-backed.

**Q6 — RFC 2119 transfer.** Only the *distinction* (normative vs informative, and "what may I rely on") transfers; the uppercase vocabulary does not. RFC 8174 makes keywords normative only in caps, and OASIS explicitly says non-standards notes should avoid the keywords. Non-standards projects that adopted the distinction (Semantic Versioning, Conventional Commits, the Rust Reference's normative/informative split) mostly did so via section labeling and plain prose, not boilerplate. **Skill should say:** mark what a reader may rely on; do not stamp READMEs with MUST boilerplate.

**Q8 — minimalism vs completeness.** No genuine conflict once scoped by genre: minimalism governs tutorials and how-tos (task-first, omit edge cases); exhaustiveness governs reference (incompleteness is a severest defect per Uddin & Robillard). Neither literature cites the other directly, but Meng et al. explicitly ground their guidelines in minimalism while still recommending complete reference. **Default:** apply completeness to reference-of-record pages only; apply minimalism everywhere else.

**Q9 — editing shipped text.** No documentation project states "never reword a released changelog entry" as a formal rule. The sourced analogies are release-artifact immutability (GitHub immutable releases; PyPI file immutability; Git tag immutability) and localization string-freeze. **Skill should say:** treat a released entry as immutable except for factual corrections — asserted by analogy, labeled as such.

## 7. The three-bucket split

**Sweep oracle (already enforced; agent only reports):** heading text and nesting, code-fence content and info strings, front-matter keys/values (aliases are live URLs), inline code spans, link targets, issue references. Rules 7, 20, 21, 34 rely on this. The agent must never edit these; it opens a finding.

**Linter / CI (a tool beats a prompt — default here):**
- markdownlint — heading increment (MD001), duplicate headings/anchors (MD024), fenced-code-language (MD040), link fragments; enforces the skeleton hygiene the oracle assumes.
- Link/anchor checking — `lychee` or `markdown-link-check` for dead links and broken `#anchors`.
- Doctest runners — `cargo test --doc`, `python -m doctest` / `pytest --doctest-modules`, Sphinx doctest, `mdbook test`: Rules 6 and 32.
- Coverage/interface lints — `interrogate`, `pydoclint`, `darglint`, `docsig`: Rule 9 (missing member docs), signature/param agreement.
- `griffe` — detects API breaking changes between versions (feeds Rules 3/28/32).
- DOCER (github.com/wesleytanws, released as a GitHub Action) — outdated code-element references: Rule 4, and the closest usable "claim checker."
- Vale — terminology/marketing-language patterns: Rules 2 (as a hint), 19.
- A project-specific tag-vs-changelog check: Rule 13.

**Agent skill (judgement or source-comparison required — a tool cannot do it reliably):** Rules 1, 5, 8, 10, 11, 12, 14, 16, 17, 18, 22, 23, 24, 25, 26, 27, 29, 30, 31 (heuristic layer above the linter), 33, 35. These need reading the page against the source and deciding intent — exactly what the research inconsistency detectors attempt and mostly fail at (DocPrism precision 0.62; DocChecker sub-random on the independent CASCADE set), so the agent's structured, report-only approach is the pragmatic substitute, not a solved automation.

Justification for leaving Rule 31 partly to the agent: MPChecker reaches 92.8% recall but only for multi-parameter constraints in Python data-science libraries (public at github.com/ParsifalXu/MPChecker); until a general, maintained config-key checker exists, the agent handles the general case and defers exact-match to a linter where the project has one.

## 8. Baseline audit

**§1 (spec not implementation; state not route).** *Supported.* Uddin & Robillard rank incorrectness and outdatedness among the severest, blocker-class defects (six of ten problems were "blockers"); DOCER shows the failure mode is real and silent (28.9% of top-1000 GitHub projects currently carry an outdated code reference). The "could this sentence stop being true without a caller noticing" test is sound and is the skill's best single idea. *Neither supported nor contradicted:* the specific slot vocabulary is one repo's framing.

**§2 (slots: Claim/Contract/Rationale/Use).** *Asserted from one repository's practice.* No source prescribes these four slots. Meng et al. weakly support "claim first" (opportunistic readers scan). Keep it as house style, not an evidence-backed rule; do not present it as derived.

**§3 (first paragraph carries the section; nobody enters at the top).** *Supported in spirit, overstated in letter.* Meng et al. confirm opportunistic/pragmatic readers enter mid-page and scan for the relevant snippet — so "open with the claim" is backed. But "nobody enters a documentation set at the top" is an overstatement: systematic readers do read top-down. **Fix:** soften to "many readers enter mid-page; front-load the claim so they can decide in one line." The baseline flags this as weak; it is — the direction is right, the absolute is wrong.

**§4 (genre table; one page one genre).** *Contradicted as stated.* Diátaxis's own compound-documents position and every real README/migration guide refute "one page, one genre." The per-genre failure modes are useful and largely correct (reference→implementation drift, changelog paraphrasing the diff). **Fix:** demote to "one primary purpose per section"; keep the failure-mode list as detection heuristics. This is the baseline's weakest section and it knows it.

**§5 (headings as anchors).** *Asserted from mechanics; unstudied.* The mechanics are correct and the two exceptions (new heading; pinned anchors) are exactly right. But there is no measurement of intra-doc-set anchor rot, so the "breaks every inbound link silently" claim should be labeled mechanics, not evidence. DOCER measures a *different* rot (code refs).

**§6 (text a tool reads; code is an unchecked claim).** *Strongly supported.* The doctest family is precisely the mechanism that converts the unchecked claim into a checked one. **Missing that the sources say should be there:** the baseline never names the doctest runners or the CI bucket — the single biggest omission the sources fill. Add: "if the project has a doctest harness, a fence is a test; if not, it is unverified prose."

**§7/7a/7b (when to write nothing; editing; comparing versions).** *Supported and unusually strong.* The "did the promise change, not the code" test aligns with the spec/implementation distinction.
