# Close the Reader Gap: Who Opens a Documentation Page, What They Hold, and What a Change Owes Each of Them (Pass 3)

## 1. Executive summary

Six of the seven candidate reader rows survive intact and the seventh is a boundary case, not a refutation; the model is sound but almost entirely *asserted*, not *studied*. No study observes documentation readers partitioned by the situation they arrived with. What the literature supplies is adjacent and strong: it confirms that two of the situations — the troubleshooter chasing an error string (D5) and the task-doer/integrator learning an API (D2/D3) — are the most frequent, and it does so with named samples. The reader model should therefore ship as an *asserted* structuring device whose D5 and D3/D2 rows carry *studied* support for frequency, while the entry points ("enters by") remain inference from mechanics.

The reference-entry shape **does converge**. Across PostgreSQL, `man-pages(7)`, the Good Docs Project, OpenAPI, and Spring Boot metadata, four fields recur in essentially every source: **name** (as code spells it), **type/valid values**, **default**, and **description/what it controls**. PostgreSQL adds two fields the candidate list rightly flags and most style guides omit: **context** (when the value is read — startup, reload, per session) and **scope**. The literal error a bad value produces, and the "since which version" marker, are carried by a minority (man-pages carries version; PostgreSQL carries error behavior inline) and are the fields most often missing.

Several projects state a **"what a change owes the documentation"** rule, and one — OpenStack's `DocImpact` — enumerates almost exactly the promise-changing changes the brief predicted: a commit has doc impact if it is "an added/altered/removed command line option, a deprecated or new feature, a caveat." Combined with PostgreSQL's same-commit doc convention, Django's mandatory `versionadded` marker, and PR-template "user-facing / breaking change" gates, this yields a defensible scan list for a diff. Most items on that list are named by at least one source; two (a new error message, a changed limit) are inferred.

Of the twelve questions: Q1 (is it studied) is settled negatively for the situational model and positively for D5/D3 frequency; Q2, Q4, Q5, Q6, Q7, Q8, Q9, Q10, Q11 are settled by stated policy or convergence; Q3 (where each reader stops) and Q12 (measured cost of burying the common case) are **not settled** — no measurement was found, only design guidance.

## 2. The reader table, revised

| --- | --- | --- | --- |
| **D1 Evaluator** | Deciding to adopt; holds a requirement; opens README/landing; enters via repo root or registry; asks "what is this, does it do X, is it maintained, what does trying it cost." | First paragraph of README; leaves once the answer is "no" or "not yet." | *Asserted.* No study of README-reading by task; supported indirectly by README-scope conventions settled in Pass 2. |

**Verdict on rows:** Keep all seven with D-numbering. No row refutes cleanly; none splits. One addition is worth flagging but **not** promoted to a row: the *generated-API-reference reader* who lands on a single method/field page is a variant of D3+D4 and is served by the same field discipline. Label the whole table *asserted*, with D5 and D3/D2 frequency *studied*.

## 3. The reference entry

**Field union and who carries each.** Basis is *stated policy* (each named source) except the synthesis judgment, which is *inferred*.

| Field | PostgreSQL runtime-config | `man-pages(7)` | Good Docs reference | OpenAPI parameter object | Spring Boot metadata | Carried by |
| --- | --- | --- | --- | --- | --- | --- |
| **Name (as code spells it)** | yes (term) | yes (OPTIONS, bold as-is) | yes | `name` (case-sensitive) | `name` | **all** |
| **Type / valid values** | yes (bool/int/real/string/enum; `enumvals`) | via SYNOPSIS/DESCRIPTION | yes | `schema`/`type`, enum | `type` | **all** |
| **Default (with unit)** | yes (unit implicit; `pg_settings.unit`) | in DESCRIPTION | yes | via `schema.default` | `defaultValue` | **most** |
| **Description / what it controls** | yes | DESCRIPTION | yes | `description` | `description` | **all** |
| **Scope** | yes (per-cluster/session) | partial | optional | `in` (path/query/header/cookie) | partial | some |
| **When read (context)** | **yes** (`context`: internal, postmaster, sighup, superuser, user — "in order of decreasing difficulty of changing the setting") | partial (VERSIONS) | no | n/a | no | **PostgreSQL-distinctive** |
| **Error at limit / invalid value** | inline prose ("non-default settings may be rejected at startup or cause errors") | ERRORS section | optional | via responses | validation, no literal | minority |
| **Since which version** | added ad hoc | **yes** (note "the kernel or C library version that introduced the change") | optional | n/a | via deprecation | minority |
| **Deprecation / replacement** | prose | yes | optional | `deprecated: true` | `deprecation.replacement` | some |
| **Interactions** | prose + cross-link | SEE ALSO | optional | no | no | prose only |

**Recommended order** (synthesis, *inferred* from convergence; sources differ, so this is a default, not a rule): name → type/valid values → default (with unit) → scope → when read → what it controls → what happens at the limit / on invalid input (with the literal error) → interactions → since version → deprecation/replacement. This front-loads the two fields D4 opens for (default, type), matches man-pages' rule that sections appear in a fixed order, and matches PostgreSQL's practice of leading with name/type/default.

**Rationale where stated.** PostgreSQL states the *context* field's ordering rationale explicitly: contexts are listed "in order of decreasing difficulty of changing the setting." `man-pages(7)` states the version rule's rationale: "Including version information is especially useful to users who are constrained to using older kernel or C library versions (which is typical in embedded systems, for example)." OpenAPI states that "the order of fields above is recommended for defining fields in the document."

**Rule for documenting an interaction between options (Q5).** The projects surveyed do **not** converge; this is a genuine gap the trial branch hit. PostgreSQL documents interactions in **prose inside one entry with a cross-reference** (e.g., `hash_mem_multiplier` describing its relationship to `work_mem`). `man-pages(7)` pushes cross-references to a dedicated **SEE ALSO** section, "ordered by section number and then alphabetically by name." OpenAPI has **no** interaction field. Recommended default (*inferred*): document the interaction once, in the entry of the option that *overrides or gates* the other (the dominant option), and leave a one-line pointer in the subordinate entry — mirroring Pass 2's canonical-source / no-dual-sourcing rule applied within a reference set.

**Two worked entries that carry most fields.**
- **PostgreSQL `search_path`** (Client Connection Defaults, docs/current): carries name, type (string), default (`"$user", public`), scope, context, what it controls, and an interaction note ("It is never searched for function or operator names"). Quoted: *"The default value for this parameter is \"$user\", public."* Missing nothing D4 needs.
- **OpenAPI path-parameter object** (spec v3.1.0): carries name, `in` (scope), `required`, `schema`/`type`, `description`. Quoted: *"name: petId / in: path / description: ID of pet that needs to be updated / required: true / schema: type: string."*

**One entry that omits a field the reader needs.** **Prometheus `scrape_config_files`** (configuration.md) documents name, syntax, and what it controls but **omits the default/behavior-when-unset and the type/validity of the glob**. Its reference text is only: *"Scrape config files specifies a list of globs. Scrape configs are read from all matching files and appended to the list of scrape configs."* The missing field is **default / behavior when unset**, which is exactly what D4 opens the page to learn.

## 4. Placement and the documentation a change owes

**Source of truth (Q7).** *Stated policy.* Kubernetes treats the generated API reference as the source of truth for API objects and their fields (settled in Pass 2 as the canonical-source rule). Spring Boot's rule is explicit and machine-enforced: the metadata "is generated automatically at compile time by processing all items annotated with `@ConfigurationProperties`," and hand-written `additional-spring-configuration-metadata.json` is *merged* into it — "If you refer to a property that has been detected automatically, the description, default value, and deprecation information are overridden, if specified." So code is canonical; the hand-written file supplies only what the annotation processor cannot see. PostgreSQL, by contrast, maintains three lists by hand (`guc.c`, `postgresql.conf.sample`, `config.sgml`) synchronized manually — its own wiki flags this as a hazard ("GUCS lists are kept in 3 different places … which are only synched with each other manually").

**Ordering conventions.** *Stated policy.* `man-pages(7)`: sections appear in a fixed prescribed order, and SEE ALSO "should be ordered by section number and then alphabetically by name." PostgreSQL groups options by topic (Connection, Resource Consumption, WAL…), not alphabetically. No single ordering rule generalizes; recommend by-topic within a page and alphabetical only within a flat option table.

**Mechanisms that enforce documentation on a change (Q8).** *Stated policy* for each:
- **OpenStack `DocImpact`**: a commit-message flag that auto-creates a docs bug. It names its triggers verbatim: doc impact exists if the commit is "an added/altered/removed command line option, a deprecated or new feature, a caveat, if you've written docs in the patch, or if you're just not sure."
- **PostgreSQL / Git / Django**: documentation ships in the *same* commit/patch as the code. Django additionally *requires* a `.. versionadded:: X.Y` or `.. versionchanged:: X.Y` marker on any new/changed feature, and mandates these blocks be self-contained so they can be removed after two releases.
- **PR-template gates**: the widely-copied Angular-style template asks "Does this PR introduce a breaking change? (What changes might users need to make in their application due to this PR?)" and carries the checklist item "Docs have been added / updated (for bug fixes / features)." Microsoft Learn and GitLab document `needs-docs`-style review gates; templates are "advisory only" unless backed by branch policies.

**Derived scan list for a diff** (an agent should scan a change for each; **named** if a source enumerates it, **inferred** if not):
1. A new or removed option/flag/env var — **named** (OpenStack; PR templates).
2. A changed default — **inferred** (implied by "altered … option"; not named as its own item).
3. A new or changed error message / exception — **inferred** (no source names it; the D5 evidence makes it load-bearing).
4. A changed limit or range — **inferred**.
5. A new mode — **inferred** (subset of "new feature").
6. A deprecation or replacement — **named** (OpenStack "deprecated feature"; Django `versionchanged`/deprecation).
7. A changed behavior of an existing option — **named** ("altered … option," OpenStack).
8. A breaking change requiring user action — **named** (Angular-style PR template).

**The troubleshooter's path (Q9).** Three shapes exist, each demanding something of the code (*stated policy*):
- **Error carries a stable code the docs index.** `rustc --explain E0592` maps a code to a long-form Markdown explanation stored in `compiler/rustc_error_codes`; Rust's own rule: "give an error a code (with an associated explanation) if the explanation would give more information than the error itself." Requires: a stable code.
- **Error carries a URL.** Next.js prints a docs URL of the form `nextjs.org/docs/messages/<slug>` (e.g., "A null error was thrown, see here for more info: https://nextjs.org/docs/messages/threw-undefined"); its contributing guide states the design intent: "This allows the logged message to be short while giving a broader description and instructions on how to solve the warning/error on the documentation." Requires: a stable slug/URL emitted by the code.
- **Reference entry or troubleshooting page quotes the literal error.** PostgreSQL's `HINT`/`DETAIL` fields and inline "may be rejected … or cause errors" prose; the Good Docs Project and DITA 1.3 both ship a dedicated troubleshooting topic (DITA's `<troubleshooting>` structures "a condition or symptom … a cause … a remedy," i.e., cause–remedy pairs); Red Hat's KCS solution shape uses Issue / Environment / Resolution / Cause (rendered "Root Cause" in the portal). Requires only that the page quote the error string verbatim so search matches it.

No evidence was found measuring which shape is *found* more often; that stays **open**. **Default to recommend when the code carries neither a code nor a URL:** quote the literal error string verbatim in the reference entry for the option that triggers it (and, if the error recurs, on a troubleshooting page keyed by the string), so the page is findable by the exact text D5 pastes into a search engine. This is the one rule Pass 2 lacked for D5 and that the change-description skill already applies to changelog entries.

## 5. Structure heuristics

**Table vs. prose vs. list (Q10).** *Stated policy*, Google developer documentation style guide. The test an agent can apply: use a **table** when items have **three or more parallel fields** and the reader compares across them — "Tables are ideal for presenting data with three or more related pieces of information per item"; "Use tables only to present two-dimensional data." Use a **list** for single-field items or term/definition pairs — "If you have only one column in your table, turn the table into a list," and "Don't use a list to show only one item." Use **prose** when items are not parallel or carry conditional logic. Redish's *Letting Go of the Words* (Ch. 9/11, "Lists and tables: what's the difference?") corroborates at the trade-book level, but I found **no measured reading study** quantifying the effect; the rule is design guidance, not measurement.

**Heading and page granularity (Q11).** *Stated policy.* Headings are anchors (Pass 2, settled), so the operative rule is "if a reader would search for it, it earns a heading." Kubernetes assigns one page-content-type per page (Concept, Task, Tutorial, Reference) and says a task page "shows how to do a single thing" and "can be short or long, provided it stays focused on one area" — a task earns a page, a sub-step earns a `##`/`###`. Diátaxis prescribes that reference architecture "reflect the structure or architecture of the thing it's describing" — one reference entry per code object. No source sets a hard length limit; splitting is triggered by mixed purpose, not word count (consistent with Pass 2's "one primary purpose per section").

**Progressive disclosure (Q12).** *Stated policy / asserted.* Diátaxis and the Good Docs reference guide both favor the common case first with the escape hatch under its own heading; Google's prescriptive-documentation guidance says "scenarios/procedures reflect the most likely use cases" and "commands/arguments serve the most common use case." Redish's "grab and go" model implies the same. But I found **no measurement** that burying the common case behind the complete case costs readers; the ordering rule is sound design guidance, basis *asserted*. Recommend: common default first, rare interactions in a table under a later heading.

## 6. Test of the reader model

**Reference page — PostgreSQL "Client Connection Defaults" (docs/current/runtime-config-client.html).** Serves **D4** primarily and **D3** secondarily. The first paragraph of the `search_path` entry answers D4's first question (what it controls, and the default: *"The default value for this parameter is \"$user\", public"*). **D5 leaves without an answer:** the page does not quote the literal error a bad `search_path` produces ("An error is reported if the search path is empty" is close but not the verbatim runtime string), so a troubleshooter searching the exact message lands elsewhere. The questions discriminate: excellent for D4, silent for D5.

**Feature page — Kubernetes task page (e.g., "Configure a Pod to Use a Volume for Storage").** Serves **D3**. Its first steps answer "how do I do X"; Kubernetes' own content-type rule keeps explanation out ("if you need to provide a lengthy explanation, you should do that in a concept topic"). **D1 and D4 leave unsatisfied:** an evaluator gets no "is this maintained / what does it cost," and a configurer gets no exhaustive field table (that lives in the generated API reference). Correct by design — the split is intentional, confirming that the reader questions map onto Kubernetes' page types.

**README — the standard-readme / purposeful-readme shape (Pass 2).** Serves **D1** and routes **D2/D7**. The first paragraph answers D1 ("what is this"). **D5 always leaves:** a README is never the page that answers an error string. This confirms D5's entry point is search, not navigation, and that a README owes D5 nothing but a link to where errors are indexed.

**Two merged PRs that added a configuration option.**
- **PostgreSQL, commit `9877374` — `idle_session_timeout`.** The scan list would demand: new option (1), its default (2), scope, when-read/context, and interaction with the sibling `idle_in_transaction_session_timeout`. What the commit actually changed: it edited `doc/src/sgml/config.sgml` in the same commit, adding a full reference entry that states the behavior and explicitly contrasts the sibling option ("This GUC variable works much like idle_in_transaction_session_timeout … But it applies when we're not in a transaction, rather than when we are"). Result: items 1, 2, scope, context, and the interaction all satisfied; no new error message (item 3) applied. The scan list matched what a careful maintainer already did.
- **Prometheus, PR #12019 — `scrape_config_files`** (merged 2023-03-07 as commit `c4da9cd`, shipped in v2.43.0). The scan list would demand: new option (1), default/behavior when unset (2), type/valid values, interactions. What the PR actually changed: it edited `docs/configuration/configuration.md` in the same PR, adding the YAML syntax and a one-line description — but **omitted the default/unset behavior and the glob's validity rules**, and a reviewer flagged the text as "a little bit vague." Here the scan list *discriminates*: it would have demanded item 2, which the merged docs did not supply. This is exactly the D4 gap §3 predicted.

The purpose is met: the questions separate a page that serves a reader from one that leaves them, and separate a diff whose docs are complete from one whose docs are not.

## 7. Conflicts

- **Does the README carry the option table?** *purposeful-readme* (Pass 2) says the README stays minimal and links out; PostgreSQL-style projects keep options only in the reference; some smaller projects put a full options table in the README. Better supported: minimal README + canonical reference (Pass 2 canonical-source rule). **Default:** the README links to the reference; the option table lives in the reference. A project must decide for itself only if it ships *no* separate docs site.
- **Where does an interaction get documented — both entries, or one with a link?** man-pages (SEE ALSO, separate section) vs. PostgreSQL (prose in one entry). Better supported for avoiding drift: one entry (the gating option) with a pointer from the other, per Pass 2's no-dual-sourcing rule. **Default:** document once in the gating option; link from the subordinate.
- **Field order.** Sources differ (PostgreSQL leads name/type/default; OpenAPI recommends its own order; Good Docs is flexible). No source's order should be presented as *the* rule. **Default:** the §3 order, explicitly labeled a house default.
- **Is the reference generated or hand-maintained?** Spring Boot/Kubernetes generate; PostgreSQL/man-pages hand-write. Generated text is authoritative for name/type/default but **misses** rationale, interactions, and the literal error — precisely what a hand-written page must add. **Default:** generate the mechanical fields, hand-write what the generator cannot see, and never let the hand-written copy restate a generated field. The drift risk is quantified: Wan et al., *Detecting outdated code element references in software repository documentation* (Empirical Software Engineering, 2023, DOI 10.1007/s10664-023-10397-6) found that "28.9% (265/918) of the projects contain at least one outdated document," with 82.3% outdated at least once and references outdated for 4.7 years on average (DOCER, top-1000 dataset; Pass 2).

## 8. What the synthesis should be told

Carry into the skill, by section:
- **Reader table (new section):** all seven D-rows as an *asserted* structuring device. Attach the *studied* frequency evidence to D5 (Xia et al. 2017: error-message search is among the most frequent tasks) and to D2/D3 (Robillard & DeLine 2011, 440+ developers; Xia et al. 2017, 235 surveyed). Do **not** promote any row to *studied* as a situation — no study observes readers partitioned this way.
- **Reference-entry field list (reference-authoring section):** the §3 union, with the four universal fields (name, type/values, default, description) as the floor and PostgreSQL's *context* and *scope* as strongly recommended. Present the order as a **house default**, not a rule, because sources differ.
- **Interaction rule:** document once in the gating option, link from the subordinate — an application of the settled canonical-source rule, not a new claim.
- **What-a-change-owes scan list (review section):** the eight-item list, each item carrying its basis label (named vs. inferred). This is the pass's main contribution to the "update the docs so they answer users' new questions" task.
- **Troubleshooter rule (D5):** a page must be findable by the literal error text; when the code emits neither code nor URL, quote the error string verbatim in the triggering option's entry. This closes the Pass 2 gap for D5.
- **Structure heuristics:** the Google table/list test as a rule; heading/page granularity as "one purpose per section, a heading for anything a reader would search"; progressive disclosure as design guidance labeled *asserted*.

Do **not**: add wording/voice/tense rules (companion `english-developer-style`); re-derive the changelog entry (companion `change-description-authoring` — stop at the D6 boundary); present a single field order or template as normative where the sources diverge; or claim Q3 (where readers stop) and Q12 (cost of burying the common case) as measured — both remain open, supported only by design guidance.
