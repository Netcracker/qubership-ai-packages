# Research: which review axes a pull request needs

A review can check a pull request along many axes: tests, user documentation, doc comments, the change description,
performance, security, backward compatibility, and more. Running a focused reviewer per axis on every pull request costs
too much, and a single reviewer misses what it was not told to look for. This research measures how well cheap
classifiers predict, from the pull request as submitted, which axes need a focused check, and whether the review should
be split across focused subagents or done by one.

The experiment ran on 2026-09-25 on 37 pull requests from `pgjdbc/pgjdbc`, `uber/NullAway`, and `apache/calcite`.
[results.md](results.md) holds the numbers and [dataset.md](dataset.md) the pull requests; both are generated by
`scripts/report.py`.

## Why

In [apache/calcite#5278](https://github.com/apache/calcite/pull/5278) the build moved to a JDK 25 toolchain, and the
documentation that still named JDK 8 for building and releasing Calcite was updated only after a reviewer asked (commit
`b2d2b36`). A reviewer who had been told "this change owes a documentation check" would have caught it before. The
question is how to produce that instruction for every pull request at a cost below the review itself.

## Method

### Axes

[prompt-rubric.md](prompt-rubric.md) defines 16 axes and three labels per axis: `2` required, `1` glance, `0` skip. An
axis is required when the kind of change mandates the check (a supported JDK version changed, so the docs owe an update)
or when the initial version has a concrete defect or omission on that axis. The rubric also asks for a review plan:
`single` or `split`, with groups of axes per subagent. The axis list is a working set, not a final one.

### Pull requests

36 merged pull requests created after 2025-03-01 were sampled, 12 per repository, stratified by size and preferring
ones with review activity. In `pgjdbc/pgjdbc` two dependency updates and one translation were then swapped for three
pull requests with a security fix, a feature, and a user-visible error; `apache/calcite#5278` was added by hand. Each
is pinned in `dataset/prs.json` by three commits:

- `base_sha`: the base of the pull request.
- `initial_sha`: the version as submitted, whose files and diff every classifier sees. It is the head before the first
  force-push after the first review feedback, or the last commit before that feedback, or the final head when nobody
  reviewed. For `apache/calcite#5278`, still open, it was set by hand to `3f06c09`, the commit before the docs fix.
- `final_sha`: the version after review, which only the labeler sees.

### Ground truth

A Claude Opus 5.5 (`claude-opus-5-5`) agent per three or four pull requests labeled every axis with hindsight: it read
the review comments, the commits after the initial version, the final diff, and the repository at the base commit,
and it also judged what a focused reviewer should have raised that nobody did. The instructions are in
[prompt-labeler.md](prompt-labeler.md); the labels, each with its evidence, are in `labels/claude-opus-5-5/`. A second,
independent Opus run labeled 12 of the pull requests (`labels/claude-opus-5-5-rerun/`); the agreement on "required"
is Cohen's kappa 0.86, which is the ceiling a classifier can be measured against.

### Classifiers

Every classifier sees the same input, built by `scripts/common.py`: title, description, file list with line counts,
and, depending on the variant, the initial diff cut to 4k, 8k, or 24k characters. `classifiers.json` lists each variant
with its model, input, and the command that reproduces it. The scripts here are cleaned-up ports of the ones that
produced the committed predictions: same prompts, questions, and inputs, apart from GitHub now printing the `index`
hashes of a diff three characters longer. A rerun is comparable, not byte-identical: older predictions lack a few
bookkeeping fields the ports write, such as `usage.items` for Codex.

- `heuristic`: path and keyword rules, free.
- Jev (`jev-1.13.0`), TypeSafe's System One model: one typed question per axis, answered with probabilities. Variants
  vary the question type (0-2 score or yes/no), the diff length, and a short project profile
  (`dataset/profiles.json`: where the docs live, when the changelog is written, who the users are).
- CLM-v0.1-8B, an open System One model, run locally on an M1 Max with the same questions as Jev.
- Claude Haiku 4.5, Sonnet 5, and Opus 5.5 through `claude -p` with no tools, and GPT-6 Luna at three reasoning
  efforts through `codex exec` in a read-only sandbox with MCP servers and web search off: one call per pull request,
  the rubric as the system prompt, JSON out.

## Findings

- **Jev is the classifier to use.** With a yes/no question per axis, the project profile, and 8k of diff it reaches AUC
  0.94, and at a threshold tuned on two repositories and applied to the third it flags 4.2 axes per pull request with
  precision 0.76 and recall 0.81. It costs $0.0002 per pull request and answers in under a second.
- **The cheaper generative models are not better, and they cost about 7 to 290 times more.** Sonnet 5 and GPT-6 Luna at
  high effort reach AUC 0.91. Haiku 4.5 reaches 0.87, flags too few axes on its own labels, and takes about a minute per
  pull request because it thinks by default. Luna at medium or low effort answers in 16 seconds instead of 39 and loses
  0.02 to 0.03 AUC.
- **Opus 5.5 scores highest, and the number is biased.** It reaches AUC 0.98, but the labeler is the same model, so
  part of that agreement is shared judgment rather than accuracy.
- **CLM-v0.1-8B does not work zero-shot on this task.** Its best variant reaches AUC 0.72, below the free heuristic.
  With the custom answer texts it rates almost every axis as required.
- **Most required checks follow from the kind of change.** 132 of the 149 required axis-PR pairs are mandated by the
  change type; 17 are defects on an axis the change type does not flag. Every classifier except CLM finds the second
  kind at recall 0.59 or below; CLM reaches 0.82 to 1.00 only because it flags nearly every axis.
- **Jev is weakest on contradictions, backward compatibility, user documentation, and the change description**, with
  AUC 0.74 to 0.88 on those axes against 0.90 or more on most others. Sonnet 5 and GPT-6 Luna do better on backward
  compatibility (up to 0.87), and Luna on user documentation (0.83 to 0.97). A stronger model could be spent only on
  these axes, where Jev is unsure; that cascade is not measured here.
- **A size rule decides single versus split about as well as the best classifier.** Splitting pull requests with more
  than 500 changed lines matches the labeler on 33 of 37 and finds 7 of the 9 to split. GPT-6 Luna on metadata matches
  35 of 37; the recommended Jev variant's own split question finds only 4 of the 9.
- **The Calcite docs case.** P(required) for user documentation on `apache/calcite#5278` is 0.94 for GPT-6 Luna at
  high effort, 0.90 for the heuristic (the keyword `JDK`), 0.70 for Opus, 0.57 for the recommended Jev variant, which
  is below its tuned threshold of 0.75, and 0.15 and 0.20 for Haiku and Sonnet. [results.md](results.md) lists every
  classifier.

## Caveats

- 37 pull requests are few. The confidence intervals in [results.md](results.md) come from a bootstrap over pull
  requests; differences of 0.01 to 0.02 AUC are within them.
- The ground truth is one model's judgment, checked once against a rerun of the same model. A labeler of another family
  would remove the bias toward Opus.
- In several Calcite and NullAway pull requests the author pushed review fixes as new commits and squashed them only
  later, so the "initial" version, taken before that force-push, already contains part of what review asked for. The
  labels still count those requests; the classifiers had less to see, equally for all of them.
- The title and description come from the pull request as it is now, not as submitted; an edit made during review
  reaches the classifiers.
- Costs are list prices. The Claude runs include about 3.5k tokens of `claude -p` overhead per call, and the Codex runs
  about 18k tokens of Codex's own prompt, mostly cached. A direct API call would be cheaper for both.
- CLM ran on transformers and Apple MPS instead of its reference vLLM setup. The model card's ranking example
  reproduces to three digits; its other published examples disagree with each other.

## Layout

| Path | What it holds |
| --- | --- |
| `prompt-rubric.md` | The axes, the labels, the review plan; also the classifiers' system prompt |
| `prompt-labeler.md` | The labeler's instructions; the local paths are placeholders |
| `dataset/prs.json` | The pull requests: links, pinned commits, size, one-sentence summary |
| `dataset/profiles.json` | The project profiles given to the profile variants |
| `labels/<model>/` | Ground truth, one file per pull request, with evidence per axis |
| `preds/<classifier>.jsonl` | One line per pull request: the prediction, its cost and latency |
| `classifiers.json` | Every classifier variant: model, input, the command that reproduces it |
| `results.md`, `dataset.md` | Generated by `scripts/report.py` |
| `scripts/` | Fetching inputs, the classifiers, the report |
| `cache/` | Fetched diffs and review threads; not committed |

## Adding a classifier

1. Fetch the inputs once: `python3 scripts/fetch_inputs.py` (needs an authenticated `gh`). It writes
   `cache/dossiers/` and `cache/views/` at the pinned commits.
2. Write the predictions to `preds/<id>.jsonl`, one JSON object per line and per pull request, through `Preds` in
   `scripts/common.py`: it keeps the lines sorted by key, rounds floats to 6 decimals, and lets an interrupted run
   resume. Each object carries `key` and `axes`, where each axis has either `p` (a distribution over `"0"`, `"1"`,
   `"2"`, plus `score`) or `label` and `p_required`; either `plan_split` (a probability) or `plan.mode`; and
   `cost_usd` and `latency_s`. The existing `scripts/classify_*.py` write this shape; `scripts/questions.py` and
   `scripts/llm_prompt.py` hold the questions and the prompt to reuse, so that a new model is compared on the same
   input.
3. Add an entry to `classifiers.json` with the id, family, model, input, runner command, and run date. The order of
   entries is the order of the rows; the bootstrap is seeded by the id, so a new entry leaves the other rows unchanged.
4. Run `python3 scripts/report.py` and commit the regenerated `results.md` and `dataset.md` with the predictions.

A new labeler goes under `labels/<model>/` and is compared to the current ground truth by changing `RERUN_DIR` in
`scripts/report.py`.
